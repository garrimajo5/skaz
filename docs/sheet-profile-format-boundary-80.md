# Граница черновика распознавания и профиля v15

Backend-сверка для [#80](https://github.com/garrimajo5/skaz/issues/80) и [#82](https://github.com/garrimajo5/skaz/issues/82) на `4888d0d`. Приложение принимает ручной профиль `manual-2014`. Экран сверки пока работает как прототип. Этот документ описывает проверенную границу и предлагаемую приёмку будущего подключения. [Контракт распознавания](sheet-recognition-contract.md).

## Что выдерживает текущий формат

| Вход | Результат |
| --- | --- |
| Явные 0 текущих и временных хитов, 0 золота | Создание, экспорт и импорт v15 сохраняют нули. Максимум хитов в v15 имеет нижнюю границу 1. |
| Явный `null` в текущих, максимальных, временных хитах или золоте | Создание отклоняет значение. Импорт v15 также отвечает 422. RAM-проверка импорта с `tempHp:null` сохраняет исходные игру, ревизию и число кампаний. |
| Старый файл без поля `tempHp` | Поле отсутствует и после повторного экспорта v15. Историческое правило команды урона читает этот пропуск как отсутствие временных хитов. С известными 12 хитами удар на 1 даёт 11 и записывает числовые 0 временных хитов с одной квитанцией при повторе. Явный `temporaryBefore:null` команда отклоняет. |
| Уровень отсутствует или равен `null`, список счётчиков равен `null`, текущий остаток или максимум строки равен `null` | Все пять вариантов импорта отклонены до создания кампании, с сохранением исходной игры. |
| Ручной счётчик с остатком 0 или сверенный пустой массив счётчиков | Оба представимы и переживают перенос. Для остатка 0 трата отклоняется без изменений, ручное восстановление даёт 1. Ячейки демо-шаблона недоступны при действующем ручном листе. |
| Весь `characterSheet` равен `null` | Это существующий режим без ручного листа: `actorLevel` и пульт используют шаблон. Он не подходит для представления ручного листа с неизвестным уровнем. |
| Строка PDF сообщает число потраченных ячеек | Исходное прочитанное число и смысл метки хранятся при сверке. Остаток выводится после подтверждения смысла и известного максимума. Поле текущего остатка счётчика v15 принимает уже вычисленное или введённое число. [Смысл Slots Expended](sheet-recognition-contract.md#дополнение2111-подпись-расхода-и-pdf-поля). |

Круг в RAM использует реальные `createCharacter`, `exportActive(15)`, `importActive`, `changeResource` и `changeCharacterCounter`. Прежние тесты подтверждают нули, игровые предупреждения, конфликт и безопасный повтор. Два новых случая покрывают пропуск старого поля, импорт неизвестной строки и перенос сверенного пустого списка.

```sh
node --test tests/manual-character-create.test.mjs tests/health.test.mjs tests/death-saves.test.mjs
```

## Требуемые входы для игрового результата

| Действие | Какие данные нужны | Когда нужных данных ещё нет |
| --- | --- | --- |
| Показать здоровье, урон, лечение | Для числовой полосы нужны текущие и максимальные хиты. Урон требует текущих и временных хитов для вычисления нового остатка, максимум нужен для вывода о мгновенной смерти. Лечению нужны текущие хиты и ограничение максимумом. | Показать известную часть с отметкой у неизвестной. Рассчитывать только определённые этой операцией исходы, остальные уточнять. Доступен ввод сверенного результата. |
| Обычный успех или провал спасброска от смерти | Известные 0 текущих хитов и отдельно сверенное состояние «при смерти». Для отметки обычного броска максимум сам по себе не требуется. | Не активировать спасброски из неизвестного остатка и не выводить состояние из неполной записи. Сейчас `Health.deathState(null)` даёт тот же результат, что при нуле, а `Health.project` требует числовой максимум и числовые временные хиты для всех веток. Поэтому изменение одного валидатора недостаточно. |
| Длительный отдых | Действующий сценарий присваивает `hp = maxHp`. Демо-ресурсы восстанавливаются по фиксированным значениям, ручной лист использует собственный путь. | Не присваивать неизвестный максимум текущим хитам и не предполагать восстановление неизвестных источников. Сверенное восстановление конкретного ресурса остаётся доступно по его собственным данным. |
| Сотворение, подготовка и приращение ресурсов | Для игровых расчётов нужны соответствующий класс и его уровень, а для списания — выбранный источник и известный остаток. Сегодня команда очереди сравнивает одновременно остаток и максимум, а `sheet:null` включает шаблон. | Сохранить известные ручные счётчики и ручную подготовку, обозначить отсутствующий вход расчёта. Известный 0 — исчерпанный ресурс, неизвестный остаток — повод его сверить. Сохранить связанные ручные источники и уже принятые исключения. |
| Кошелёк и запись награды | Для вычисления нового баланса из приращения нужен известный прежний баланс. Текущий клиент прибавляет награду непосредственно к `state.gold`. | Дать посмотреть и записать полученную награду с ручной сверкой баланса без подстановки 0. |
| Экспорт, импорт и отмена | Значение и происхождение должны пережить запись, повтор команды с тем же ID и перенос. Старый формат уже умеет отказать в экспорте при потере данных. | Читаются прежние пакеты с их исторической семантикой. Для нового неизвестного нужен явно различимый формат. Экспорт в v15 должен объяснить несовместимость, если значение нельзя передать без потери. |

См. [игровую сверку хитов](design/sheet-recognition-game-review-80.md#когда-неизвестные-хиты-влияют-на-действие--24112026) и реализацию [общего расчёта](../client/health.js), [ресурсных команд](../server/resource-operations.mjs), [ручного листа](../server/character-sheet.mjs) и [переноса](../server/transfer.mjs). Для реализации #82 результат общего расчёта должен хранить причину недоступности отдельно от текста интерфейса. Подстановка нуля, демо-уровня или пустого списка скрыла бы источник ошибки.

## Приёмка схемы для #82

1. Согласовать один источник истины для числового и неизвестного значения в профиле. Явный `null` со сверенным происхождением и отсутствие выбора остаются разными состояниями. Отдельно согласовать форму неизвестного списка, сверенного пустого списка и сверенных строк. Браузерный модуль сверки подключает типы JSDoc запроса, ответа и состояния при интеграции API.
2. В вымышленной игре выполнить по кругу сохранение → действие → перенос → повтор для текущих хитов `null` и 0. Добавить известные 0 с вручную подтверждённым состоянием и неизвестным максимумом, отдельно — удар с неизвестными временными, приращение неизвестного кошелька и ручной счётчик при неизвестном классовом уровне. Во всех случаях сверить отображение, технический отказ или допустимое ручное действие и сохранённое происхождение.
3. Доказать совместимость и откат на копии. Проверить обычный импорт v15 с явным 0 и старым пропуском, точный повтор создания, отсутствие частичной кампании и отказ при устаревшей ревизии. Смена формата не должна молча превращать новые `null` в значения по умолчанию. Автоматические расчёты проверять на согласованных источниках отдельно от права сохранять ручные данные.

Схема и номер формата остаются предметом согласования backend и геймдизайнера. Отчёт передаёт доказательства #80 и тестовые входы #82. #84 и #97 сохраняют зависимости. Проверка реальным распознавателем, UI с подключённым API и выпуск относятся к дальнейшим этапам.
