# Сессии и архив: серверный этап

POST `/api/sessions` начинает следующую сессию **активной кампании**. Тело:

```json
{
  "mutationId": "уникальный-uuid",
  "expectedRevision": 12,
  "session": { "name": "Возвращение к маяку", "playedOn": "2026-10-19" }
}
```

Нужны заголовки application/json и X-Skaz-Client: local-v1. Действуют Host/Origin, лимит 512 КиБ, общая ревизия и ключи повторов. Название — 1–120 символов; playedOn — существующая календарная дата YYYY-MM-DD, указанная пользователем. Время и часовой пояс из этой даты не выводятся. Для прежних безымянных сессий name/playedOn остаются null: дата создания базы не подменяет дату игры.

Операция атомарно архивирует предыдущую сессию, создаёт новую, переключает active_context, увеличивает ревизию и записывает историю/квитанцию. Повтор исходного ключа возвращает актуальный workspace и affectedContext исходной команды, не создавая ещё одну сессию. Конфликт ревизии — 409, неверные поля — 400/422. Успех — 200.

Персонаж, его ресурсы (включая концентрацию), личные заметки, карта и задания **не сбрасываются**. Начало сессии не считается отдыхом. У новой сессии пустой журнал, нет принятых событий и правок; три фиксированных демонстрационных события отмечены пропущенными, чтобы не предложить их заново как реальные. Это временная совместимость с прототипом, а не движок событий. Клиент пока позволяет вручную вернуть пропущенные демо-события. Вымышленные записи удалены из сохранённого журнала и экспорта. Заголовок использует имя/дату текущей сессии, а карточка вымышленной истории на листе помечена «Демо сюжета».

GET `/api/campaigns/{campaignId}/sessions` возвращает `{sessions:[...]}`: id, campaignId, name, playedOn, archived. Порядок — создание, не дата игры. GET `/api/sessions/{sessionId}` возвращает эти метаданные и data (journal, accepted, dismissed, eventEdits). Отсутствующая сущность — 404. Чтение архива не переключает активную игру и не меняет ревизию.

Архив содержит журнал и состояние событий сессии, **не снимок всех характеристик персонажа на ту дату**. Актуальные ресурсы остаются у персонажа. Выбор архивной сессии через POST /api/context/select запрещён (409). SQLite-триггер также запрещает изменение её data_json. Удаления, редактирования и восстановления архива пока нет.

GET /api/campaigns теперь перечисляет только неархивные сессии для переключения игр; полный список доступен отдельным методом выше. Это сохраняет работу текущей кнопки «Кампании» после начала следующей сессии. Кнопка «Сессии» открывает список, форму начала (название и дата обязательны) и просмотр журнала только для чтения. Перед началом интерфейс объясняет архивирование и сохранение ресурсов. Команды проходят через долговременную очередь клиента: при обрыве связи повторяются с тем же ключом, после перезагрузки также. При черновике начало сессии блокируется. Личные заметки показаны отдельно по смыслу: они общие для персонажа, не включаются в архив; в текстовом экспорте отмечены отдельным разделом.

Метаданные хранятся в добавочной таблице session_details; раскладка базы остаётся v2, JSON workspace — v1. SQLite backup сохраняет все сессии, метаданные и архивы; JSON экспорта прогресса — только активный журнал без истории сессий. Не запускай одновременно старый и новый сервер над одной базой; откат к коду до поддержки архивов требует отдельной резервной копии.

Проверки: сохранность ресурсов/заметок/карты/заданий; отсутствие старых событий в новой очереди; защита архивов; конфликт старого черновика; повтор команды после последующих изменений; календарные ошибки; откат частично начатой сессии; сохранность архива и квитанции после открытия/backup; HTTP-защита и чтение списков.
