# Сверка листа: эксперимент JS + JSDoc (#80)

21.11.2026. Роль frontend. Результат для Review; Node.js/SQLite сохранены. Основание: [#80](https://github.com/garrimajo5/skaz/issues/80), [контракт §4–5](../sheet-recognition-contract.md#4-поле-источник-и-ручной-выбор), [UX](sheet-recognition-ux-80.md). #97/#84 и приёмка M0 не закрываются.

## Где живёт форма и что изменено

Это **интерактивный прототип** [sheet-review-80.html](prototypes/sheet-review-80.html), не экран приложения. OCR, сохранение/перезагрузка профиля, API и выпуск не реализованы этим PR. Ближайшее нужное изменение по контракту — подтверждать точные выбранные значения и происхождение, затем обесценивать подтверждение после правки. Полный nullable payload с #81/#82 остаётся несогласованным.

Встроенный скрипт вынесен в один [JS-модуль](prototypes/sheet-review-80.js) с `// @ts-check`: данные полей, DOM-ссылки, классовое сравнение, подтверждённые числовые/неизвестные значения и происхождение описаны JSDoc. Снимок `confirmation.values` заменил булев `confirmedResult`. Общий `invalidateConfirmation()` вызывается из ввода, выбора unknown и двух путей согласования; он не перестраивает поля и не стирает ручной текст. `edited` отделён от `changed`: согласование/unknown делают черновик изменённым, но сами по себе не превращают OCR-число в ручную коррекцию.

## Воспроизведение

```sh
npm ci --ignore-scripts
npm run check:sheet-review
npm run test:sheet-review
```

Первая проверка — `tsc --noEmit -p jsconfig.sheet-review.json`, strict/checkJs. Проверяется только этот JS-файл и стандартные библиотеки (проверено `--listFilesOnly`: 1 файл проекта + 58 библиотечных); остальной клиент не типизируется. Генерации JS нет. TypeScript 7.0.2 закреплён lock-файлом как devDependency; установка на этой Windows-машине дала 2 пакета, около 30 MiB на диске, включая платформенный компилятор. В браузер и сборку приложения компилятор не попадает. Обычные Node-тесты остаются без этой зависимости: отрицательная типовая проверка вынесена в `tests/types/` и запускается отдельной командой эксперимента.

`test:sheet-review`: **20/20 PASS**, включая прежние 14 advisory/multiclass, 5 сценариев всей формы и 1 отрицательную проверку типов. `npm run check`, `npm run build` и синтаксис нового JS — PASS. Стек и сборка приложения не менялись.

Отрицательный тест копирует актуальный JS и конфигурацию во временный каталог, вносит `value:null` вместе с `selection:'corrected'/provenance:'manual-correction'`: получен **TS2322**. Числовая ручная коррекция не может быть unknown. Файлы удаляются в `finally`; намеренной ошибки и `@ts-ignore` в рабочем коде нет. Это проверка на временной копии, не порча основной формы.

## Сквозной сценарий и границы доказательства

В существующем синтетическом `conflicting-pages` максимум HP имеет `null`: страницы предлагают 33 и 27, однозначное значение не выбрано. Это не новый результат OCR. Второе неуверенное поле явно оставляется unknown.

| Действие | Наблюдение в тесте обработчиков формы |
| --- | --- |
| Открыть пример | Поле HP пусто; `selectedValue` возвращает undefined (ещё нет решения), отправка запрещена; это не 0 |
| Ввести 33 | Текст сохранён, статус «Исправлено вами»; ввод сам не подтверждает группу |
| Подтвердить | Снимок HP: 33 / corrected / manual-correction; явно неизвестное второе поле — null / left-unknown / manual-unknown |
| Исправить на 35 | Снимок становится null, общий флажок снят, прежний результат скрыт, повторная отправка запрещена; текст 35 и сам input сохранены |
| Ещё раз подтвердить | Новый снимок содержит 35; ранее полученный снимок 33 не мутировал |

Отдельно: введённый 0 остаётся числом с игровым предупреждением, без обязательного согласования мастера; неизвестное — null, отрицательное/непредставимое не подтверждается. OCR-ноль и ручное unknown сохраняют разное происхождение. Пустой набор полей не подтверждается. Запросов к OCR/профилю нет, только загрузка manifest.

Поведенческий тест исполняет полный подключаемый скрипт и его обработчики в небольшом DOM-адаптере Node. Браузерный фокус, диалоги и CSS проверены отдельным прогоном ниже.

## Браузерная проверка прототипа · 24.11.2026

Отдельный headless Chromium (Edge 158) открыл прототип на локальном стенде с вымышленными листами. На 1180×820 проверены обе страницы фрагмента, возврат фокуса по Escape, пустой максимум хитов → 33 → подтверждение → 35 → новое подтверждение. После правки старое подтверждение исчезло, 35 осталось в поле. В другом примере ноль зарядов сохранился отдельно от неизвестного числа зелий.

На 393×873 с touch, 820×1180 и 1180×820 проверены предупреждение при сумме классов 5 и ручном итоге 6, подтверждение без согласования мастера, раздельные Spellcasting и Pact Magic, снятие устаревшей отметки мастера и три темы без горизонтального переполнения.

На базе `cd9d4b2` воспроизведена потеря второго выбора. После ручной правки выберите другой пример, нажмите «Остаться», сразу откройте диалог снова и дождитесь отложенного события `close` от первого открытия до нажатия «Отбросить исправления». Второй пример не загружался. Действия кнопок теперь обрабатываются на `submit`, а Escape — на `cancel`. Тот же сценарий проходит. Обычный отказ от смены сохраняет ввод.

Проверки кода — `npm run test:sheet-review` (21/21, включая отрицательную проверку типов) и `npm run build`. Граница проверки — прототип. Android и физический планшет в этом прогоне не участвовали. OCR, сохранение и перенос профиля требуют своей реализации и приёмки.

Типы подтвердили контракт обработчика `SubmitEvent`. Потерю решения выявил браузерный тест: типы не описывают порядок нативных событий. Из кода формы изменились один JS-модуль и его поведенческий тест.

## Что дала типизация

- Помогла выразить три разных состояния: ещё не решённое/некорректное (undefined), явное неизвестное (null), число включая 0; подтверждение теперь несёт точные значения и происхождение.
- Компилятор указал на nullable выбранное поле внутри callback: обработчик источника теперь захватывает проверенную локальную ссылку. Он также потребовал явных типов DOM и строкового значения option. Это диагностика доработки, не найденные дефекты production.
- Отдельно воспроизведены на базовом 67f43b2: `selectedValue` пустой строки возвращал 0; пустые `fields` + флажок позволяли «подтвердить пример». Первое ранее ограничивал общий gate, но помощник был опасен для нового потребителя; оба исправлены. Эти семантические ошибки обнаружили чтение контракта/поведенческие проверки, **не tsc**.
- При привязке DOM обнаружено: result в HTML — div, не p. tsc не проверяет реальный HTML; добавленная runtime-проверка элемента и тест полной формы страхуют этот разрыв.

## Цена и оставшаяся ручная работа

Изменён/типизирован **1 модуль формы**, до этого встроенный в HTML; **0 модулей приложения/server**. HTML теперь подключает JS; прежние 2 поведенческих файла изменили только источник чтения и имя состояния. Добавлены 2 тестовых файла, локальная конфигурация, 2 npm-команды и dev-lock. Объём основной JS вырос с 72 встроенных строк до 227: JSDoc/DOM-привязки и разнесённые обработчики вместо длинных строк. Большую часть клиента типизировать не пришлось.

Правило сброса подтверждения раньше повторялось в changed, двух согласованиях и load; теперь реализация одна, но **все изменяющие handlers по-прежнему обязаны её вызвать**. Ограничения числа задаются в `reviewValue`, однако связь maxHP → диапазон currentHP и сравнение классов остаются явным ручным кодом. Один смысл maximum HP уже имеет два ключа (`hp.max` и `hpMax` в разных примерах): JSDoc `string` не ловит неверный выбор ключа.

Для ещё одного обычного числового поля разработчик добавляет определение/регион синтетического источника и ожидаемый сценарий; генерация input, unknown, предупреждения, provenance и snapshot общие, новых DOM-ID в ручной таблице не нужно. Для зависимого поля надо отдельно изменить update/предупреждение, проверить условие согласования, его инвалидирование и source/focus. Статические элементы повторяются в HTML и typed DOM-таблице. Тексты статусов/aria, открытие источника/возврат фокуса и discard-dialog всё ещё синхронизируются вручную. Типы не заменяют эти поведенческие/UI-проверки. Входной manifest остаётся доверенным синтетическим JSON; будущему OCR нужны runtime-проверки серверного payload, а не приведение JSDoc-типа.

## Выбор для MVP и следующая проверка

**Оставить JS + JSDoc для этого экрана**, вместе с общей функцией инвалидирования и снимком подтверждения. Сейчас цена — один локальный модуль, dev-установка/команда и поддержка описаний; нет миграции клиента, нового runtime, React или изменения Node.js/SQLite. При следующем поле типы проверят форму числа/null и происхождение, а тест сценария — ручную синхронизацию.

Данных о многогрупповой форме пока недостаточно для выбора React: прототип не получает запоздалые OCR-ответы и не восстанавливает серверный черновик. Следующее продуктовое изменение для оценки — подключение согласованного nullable payload #80/#81/#82: ручная правка HP → поздний ответ другой generation → восстановление review с прежним ручным числом и сброшенным подтверждением. Сравнить число мест синхронизации, время добавления поля, отсутствие перезаписи/focus regression и объём сборки; решение об отдельном React-эксперименте принимать по этим фактам. React в этот PR не входит.

Рефлексия frontend: основная дополнительная работа — извлечение inline-script, DOM-привязки и тест всей формы; типизация одного экрана не потянула клиент. Предложение планировщику: испытать этот же scoped check при подключении nullable payload; критерий — новый field/generation сценарий без повторной реализации unknown/подтверждения и без потери ручного ввода. Это предложение, не изменение общих инструкций/этапов.
