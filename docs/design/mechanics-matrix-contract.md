## Единица проверки

Одна строка — одна механика с устойчивым внутренним ID. Для неё обязательны:

1. Наблюдение из актуального, выбранного владельцем листа и дата. «Видно в листе» не означает «проверено по правилам».
2. Источник и редакция, место правила, статус проверки. Отдельно неизвестное происхождение, опциональная особенность и согласованное исключение мастера. Материал 2024/UA не подменяет отсутствующий источник 2014.
3. Входные значения и ожидаемый результат: расчёт, разрешённый выбор, стоимость, восстановление, длительность, ограничения и взаимодействия. Неизвестное сохраняется неизвестным.
4. Кто решает: однозначный расчёт приложения; выбор игрока; оценка ситуации мастером. Например, приложение учитывает подтверждённую стоимость, но не решает за мастера, видно ли цель.
5. Покрытие: отсутствует / ручное / частичное / проверенное, с файлом или тестом, версией и границей доказательства. Наличие теста не означает его запуск, чтение кода не означает браузерную приёмку.
6. Конкретный пробел, существующая задача либо предложение дочерней задачи; независимое QA, игровое заключение и подтверждение владельца учитываются отдельно.

Для заклинания отдельны наличие в книге, доступ от класса/предмета, подготовленность по каждому источнику, доступный круг заклинания, круг потраченной ячейки и эффект. Для предмета отдельны владение, количество экземпляров, экипировка, настройка, активная инфузия и заряд. Нельзя считать наличие текста в заметке активным эффектом.

## Обезличенные сценарии для #82/#83

Это вымышленные примеры, не восстановление личного листа.

- Два источника дают одно заклинание. Подготовка через источник A не отмечает его подготовленным через B. Снятие подготовки A сохраняет право B. У каждого свой бюджет, характеристика и фокусировка. Известные/подготовленные заклинания определяются по каждому классу отдельно — [Basic Rules 2014, Multiclassing](https://www.dndbeyond.com/sources/dnd/basic-rules-2014/customization-options).
- Общая ячейка более высокого круга не добавляет в книгу и не разрешает подготовить заклинание этого круга. Повышенный расход существующего заклинания — отдельное действие, по той же [норме 2014](https://www.dndbeyond.com/sources/dnd/basic-rules-2014/customization-options).
- Игрок выбирает класс следующего уровня. Предпросмотр показывает только получаемое этим классом, сохраняет прошлые выборы и ручные значения. Неподдержанный вариант объясняется до записи; свободное className не разбирается в угадываемые уровни.
- Импорт со старым общим статусом не назначает происхождение автоматически. До сверки статус обозначен «источник не подтверждён» и сохранён ручной путь.

## Предложения небольших задач для #85

### Составное применение заклинания от предмета

Backend, затем отдельная frontend-задача. Предпосылки: подтверждённый источник предмета/заклинания, экземпляр и настройка, если нужна. Синтетическая техническая фикстура: предмет с7 зарядами, разрешённая стоимость2, концентрационное заклинание; это модель теста контракта, не новая запись homebrew в каталоге.

DoD: после подтверждения остаётся5 зарядов, ячейки класса неизменны, концентрация заменена одной транзакцией; отмена возвращает оба состояния, если нет конфликтующего позднейшего действия. Повтор после потери ответа ничего повторно не списывает. Неизвестный остаток, недостаток зарядов, чужой экземпляр/герой, неподтверждённый источник и подмена стоимости отклоняются без записи. Последний заряд не уничтожает предмет молча: нужный бросок/решение фиксируется отдельно по проверенному правилу. Не объявлять поддержку всех предметов по одному сценарию.

### Типизированные события восстановления

Backend, затем frontend выбора события. Восстановление после короткого/длительного отдыха, на рассвете, раз в день и от конкретного действия — разные причины, а не одна кнопка «пополнить всё».

DoD: вымышленная фикстура содержит разные триггеры; каждый меняет только связанные ресурсы. Повтор события не восстанавливает повторно; неизвестная политика не угадывается из названия счётчика. Случайный результат вводит/подтверждает игрок в допустимых пределах. Отмена учитывает последующий расход и конфликт; происхождение и история переживают перенос. Время реального компьютера само по себе не означает рассвет в кампании.

Эти два предложения ещё не Ready: планировщик #85 должен проверить зависимости, связать со строками приватной матрицы и не дублировать #82/#83. Окончательный набор зависит от сверки актуального листа и решений по спорным источникам.

## Приватность и передача

Приватный черновик хранится в игнорируемом data/private/ рабочей копии исполнителя; файлы не входят в PR. Доступ следующему проверяющему — через разрешённую локальную рабочую среду либо явную передачу владельцем, не публичную ссылку. Старый снимок отмечен устаревшим после ответа владельца; новая вкладка прочитана без редактирования и игровых действий. Некоторые поля противоречат друг другу. Нельзя считать матрицу полной до ответов и проверки скрытых/неподготовленных записей; кнопка подготовки при чтении не открыла диалог, неизвестные поля не заполнены догадкой.

Проверены уникальность ID строк, ссылки вопросов на строки, наличие источников и файлов статических доказательств, отсутствие статуса самостоятельного принятия и игнорирование приватных файлов Git. Приложение не менялось; сборка и браузерный QA приложения к документу неприменимы. Просмотр LSS — чтение исходных данных, не QA настоящего героя.

Рефлексия: ранняя проверка актуальности обнаружила, что сохранённый перенос устарел, и предотвратила автоматизацию неверной базы. Предложение планировщику — в каждой матрице сохранять дату и отдельное подтверждение актуальности/полноты, не объединяя их. Польза — меньше переделок; затраты — один вопрос перед сверкой; риск — лишние повторные вопросы, поэтому повторять только при смене источника или явных изменениях. Решение планировщика ожидается.
