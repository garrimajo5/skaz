# Кампания и известные персонажи — UX-спецификация

Issue [#86](https://github.com/garrimajo5/skaz/issues/86), роль UX-дизайнер. Версия16.11.2026. **Предложение для Review**, не игровая приёмка и не выпущенная функция. [Цель](../PROJECT_GOAL.md), [M3](../ROADMAP.md), [гайдлайны](visual-guidelines.md), [темы](themes.md). Только вымышленные примеры.

## 1. До и после

Существующая основа: отдельные задания, журнал/архив сессий, история операций и места; игровые листы создаются отдельно от каталога существ. Источники: client/quests.js, server/quests.mjs, server/characters.mjs, [сессии](../sessions.md), [API](../local-api.md). Наличие персонажа в бестиарии не означает знакомство героя с ним.

| До — разрозненный сценарий | После — предлагаемый сценарий |
| --- | --- |
| Вспоминать предыдущую игру через журнал, затем отдельно искать задания | Обзор сразу показывает место остановки, активные цели и последнюю сессию |
| Сведения о знакомом остаются свободным текстом заметок | Отдельная карточка известного персонажа со связями и последней встречей |
| Сюжет и числовые изменения приходится различать по содержанию | Дневник сюжетных записей и История действий разделены явно |

Это сравнение структуры по коду/документации, не свежий screenshot текущего production. Макет не заменяет существующий режим Игры.

## 2. Информационная архитектура

В существующую навигацию добавить вход «Кампания»; внутри четыре самостоятельных раздела: Обзор, Персонажи, Дневник, История действий. Ссылки «Задания» и «Журнал» старой навигации остаются доступными и приводят к соответствующим существующим данным; не создавать вторые независимые сущности. Подробный способ размещения входа в основной оболочке согласовать с frontend, чтобы не переполнить нижнюю навигацию.

Не менять режим Игра/Подготовка неявно. Вход из Игры сохраняет героя, сессию, выбранный экран, фокус и прокрутку; «Вернуться в Игру» восстанавливает этот контекст. На планшете обзор — две колонки, на телефоне одна. Ресурсы героя не дублировать в обзоре; текущий пульт остаётся обязанностью оболочки.

Приоритет обзора: где остановились → что делать дальше → вспомнить прошлую сессию → последние встречи. Показывать до трёх активных целей со ссылкой «Все задания»; первым — первое незавершённое действие в существующем порядке этапов, без автоматической смены статуса задания/начисления награды. Если следующего шага нет, явно «Следующий шаг не указан».

## 3. Карточка известного персонажа

| Поле | Поведение |
| --- | --- |
| Имя/прозвище | Обязательно; неизвестное настоящее имя допустимо заменить наблюдаемым прозвищем. Совпадение имени предлагает сверить записи, но не сливает автоматически |
| Краткое описание | Свободное описание роли/внешности, не обязательная ссылка на статблок |
| Сведения | Отдельные записи с видом «Известно» или «Предположение»; источником может быть сессия/заметка или «не указан» |
| Отношения | Свободная заметка игрока; «отношение неизвестно» по умолчанию, а не нейтральное/враждебное |
| Последняя встреча | Последнее известное место + сессия/уточнение; не дата изменения карточки, не GPS и не текущее положение |
| Связи | Квесты, места, дневниковые записи, другие известные персонажи той же кампании; необязательны |
| Портрет | При наличии и разрешённом механизме; отсутствие не мешает чтению, генерация четырёх состояний вне M3 |

MVP хранит только сведения игрока. Не подтягивать скрытые подробности из бестиария, мастерских материалов или другого персонажа автоматически. Список игровых листов и справочник лиц кампании не объединять.

Список: имя, краткое описание, последняя встреча. Поиск по имени/прозвищу и текстам сведений; не требовать точного написания регистра. Пустой результат поиска отделён от отсутствия персонажей. После возврата из карточки сохраняются запрос и положение списка.

## 4. Основные сценарии

A. Перед игрой: Кампания → прочитать место остановки/следующий шаг → при необходимости открыть последнюю сессию → перейти по имени к карточке. Цель: вспомнить контекст без открытия истории числовых операций.

B. Встретили нового NPC: Персонажи → Добавить → имя/прозвище, короткое сведение → выбрать известное/предположение → Сохранить. Место/сессия могут оставаться неизвестными. Никаких обязательных характеристик, расы и полного портрета.

C. Новая встреча: карточка → «Добавить встречу» → существующее место либо текстовое уточнение; текущая сессия предлагается явно, игрок может выбрать прошлую/неизвестную → предпросмотр → сохранить. Номер сессии не выводится из времени создания БД. Новое наблюдение не стирает предыдущие.

D. Ошибка в записи: карточка → редактировать конкретное сведение/встречу → сохранить исправление с историей. Перевод предположения в факт — явное действие, не автоматическое следствие редактирования. Удаление/архивирование всей карточки требует отдельной постановки, не скрывается в макете.

E. Завершение игры: открыть Дневник, добавить итог сессии, затем обновить заметку «Где остановились». Завершение сессии не равно отдыху, не восстанавливает ресурсы. Сюжетную запись не генерировать из журнала урона автоматически.

F. Проверка расхода: История действий → фильтр по сессии/типу → запись «было → стало». Отмена предлагается только при разрешённой сервером операции, а не для произвольного старого события.

## 5. Состояния и защита ввода

| Состояние | Отображение и действие |
| --- | --- |
| Загрузка | Нейтральное сообщение; отсутствие данных пока не объявлять пустой кампанией |
| Нет записей | Объяснение раздела и одно действие добавления; в истории — «Пока нет действий», без кнопки создания события |
| Нет результатов поиска | Сохранён запрос, «Очистить поиск»; не предлагать импорт каталога |
| Ошибка чтения | Явная ошибка с повтором; не подменять пустым списком, не уничтожать ранее показанные данные |
| Отправка | Видимое ожидание и защита повторного submit; транспорт повторяет ту же команду |
| Потеря ответа | Сверить результат по ключу операции, не создавать второго персонажа/встречу |
| Конфликт | Сохранить локальные поля; показать новую версию и различия; повтор только после осознанной сверки. Не перезаписывать молча |
| Закрытие с изменениями | Предложить остаться либо отбросить черновик. Сохранение черновика привязано к пользователю/кампании/записи |
| Смена кампании/отзыв доступа | Не отправлять старую форму в новый контекст; убрать чужие данные, дать безопасный путь к собственному черновику в пределах прав |
| Недоступная связь после импорта | Показать текст и исходное происхождение с пояснением, не создавать фиктивную сессию и не делать чужой ID ссылкой доступа |

Текущий прототип демонстрирует часть этих состояний, а не серверные гарантии. API-реализация и интеграционные проверки — #87/#88.

## 6. Адаптивность и доступность

1180×820: обзор в двух колонках, главное слева; 820×1180 — две колонки при достаточной ширине; 390×844 — одна колонка, четыре раздела сеткой2×2, кнопки без горизонтального прокручивания всей страницы. Длинные имена переносятся, числовая история читается целиком. Диалог ограничен высотой экрана с внутренней прокруткой; виртуальная клавиатура требует отдельной Android-проверки реализации.

Минимум44px для целей касания, основной текст16px, подписи≥12px. Видимый focus-visible, логичный Tab, Escape закрывает диалог по правилам черновика, фокус возвращается к вызвавшей кнопке. Заголовок нового раздела получает фокус, поиск не теряет фокус при обновлении результатов. Факты/предположения различаются подписью, не только цветом. Сообщения об ошибках role=alert, подтверждение role=status.

Все три темы используют семантические токены. Выбранность контрастна, ошибки не окрашены как успех. Макет проверяет композицию в темах, но не сертифицирует полный computed-аудит приложения #31.

## 7. Передача разработчикам

Backend #87: предложенная сущность известного лица, отдельные сведения и встречи, scoped-связи с существующими заданиями/местами/сессиями; nullable неизвестные поля; revision/контекст/mutationId; история исправлений, безопасный перенос недоступных исходных ссылок. Названия новых endpoint и схема здесь не утверждаются: backend должен предложить контракт и ограничения размеров до frontend-реализации.

Frontend #88: сохранить существующий квестовый/журнальный поток, реализовать новые вкладки и карточки, ошибки/черновики/возврат, не копировать серверную модель из статического макета. Правила выбранной встречи при добавлении задним числом согласовать с backend и геймдизайнером: порядок определяется явно выбранной игровой сессией/порядком наблюдений, не timestamp редактирования.

Геймдизайнер: проверить, хватает ли обзора для восстановления контекста, не смешиваются ли знания игрока и мира, понятен ли выбор факт/предположение и последняя встреча. QA: сценарии A–F плюс состояния таблицы; физические устройства — отдельно. Их согласование **ожидается**, не выполнено автором UX.

## 8. Прототип и ограничения

[Самостоятельный HTML-макет](prototypes/campaign-86.html) можно открыть локально; для проверок использован только согласованный4337. Нет внешних шрифтов, API и сохранения на сервере, данные вымышлены и сбрасываются reload. Реализованы вкладки, поиск, открытие карточки, создание/правка простого сведения и демонстрационные состояния. Переход в Игру, квест и заметка места остановки пока поясняются сообщением; форма встречи/полное редактирование связей и защита черновика описаны спецификацией, не притворяются работающими кнопками приложения.

Прототип не включается в production build и не требует релиза приложения. Нельзя считать его реализацией #87/#88 или приёмкой M3.

## 9. Проверка автора UX и рефлексия

IAB: поиск «смотритель» находит Оррена; карточка отделяет предположение и последнее наблюдение. В390×844/Атлас создана вымышленная Проводница, неизвестные место/сессия остались неизвестными. В820×1180/Уголь проверены пустой поиск, ошибка/повтор, конфликт оставляет введённое имя. Альбомный1180×820/Полярис — обзор и переходы. Это проверка интерактивности макета, не независимый QA и не Android.

При проверке найдено: старое сообщение «Сохранено» оставалось при смене раздела/ошибке; очищено. В демонстрационном состоянии конфликта исчезал список; исправлено. Пустое имя из пробелов отклоняется. Проверка синтаксиса JS и локальных ссылок дополняет браузерные действия.

Рефлексия: чёткое разделение UX и backend позволило показать поток без миграции живых данных. Лишний вывод длинных строк исходников затруднил обзор; предложение планировщику — ограничивать поиск сначала именами файлов, затем конкретными диапазонами. Дополнительная рекомендация: задачи UX должны иметь явные уровни готовности «спецификация / макет / проверка автором / независимая приёмка», чтобы не объявлять интерфейс выпущенным по скриншоту.
