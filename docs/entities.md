# Кампания, персонаж и сессия: хранение v2

При открытии базы v1 сервер переносит текущую игру в связанные таблицы и назначает UUID каждой сущности. Повторное открытие не меняет ID. Сервер поддерживает создание и переключение игр; интерфейс управления пока не подключён. Модель механик по-прежнему ограничена демо-бардом.

| Сущность | Данные |
| --- | --- |
| campaigns | Название, заметки карты, состояния этапов заданий, ruleset=5e-2014 |
| characters | Имя, описание, хиты, золото, ячейки, вдохновение, концентрация, личные заметки; campaign_id |
| sessions | Журнал, принятые/пропущенные демонстрационные события и их правки; campaign_id |
| active_context | Активные campaign_id, character_id, session_id |

Составные внешние ключи не позволяют назначить в активную игру персонажа или сессию другой кампании. Это целостность связей, а не авторизация: пользователи, членство и видимость ещё не реализованы. У старых заметок нет достоверных сессий происхождения; личные заметки остаются у персонажа, текущий журнал переносится целиком в одну сессию. Время начала и номер сессии не выдумываются. Заголовки демо-сессии в клиенте пока фиксированы.

## Совместимость и миграция

Версия **раскладки SQLite** хранится в workspace.schema_version и теперь равна 2. Версия **формата JSON/API** остаётся 1: существующие экспорты, клиент и черновики совместимы. Чтение `/api/workspace` собирает состояние из сущностей. `workspace.state_json` сохраняется как совместимый полный снимок последнего подтверждённого состояния; основное чтение не использует его. История `changes` не переписывается, старые ключи повторных запросов продолжают работать.

Миграция выполняется внутри BEGIN IMMEDIATE: проверка исходного состояния, создание таблиц, перенос и смена версии либо завершаются вместе, либо откатываются. Новый запуск сервера не следует совмещать с работающим старым процессом. Перед обновлением останови старый сервер и сделай SQLite backup старой версией. Откат на старый код требует восстановления копии базы v1: старый код не поддерживает раскладку v2. При восстановлении сохраняй также текущую v2, если после переноса уже были изменения.

Обычное сохранение атомарно обновляет сущности, общий снимок, ревизию и историю. Чтение использует один SQL-снимок для всех сущностей и ревизии. Локальный JSON-импорт заменяет содержимое текущей игры с сохранением её ID. SQLite backup включает ID и связи; JSON-экспорт прогресса их не переносит. Каталог хранится независимо.

GET `/api/context` возвращает `revision`, `updatedAt`, `ruleset` и объекты `campaign`, `character`, `session`: каждый имеет `id` и `data`; персонаж и сессия также `campaignId`. Ответ GET `/api/workspace` дополнительно содержит `context: {campaignId, characterId, sessionId}`. Изменения ресурсов проходят через прежний PUT `/api/workspace`.

## Создание и переключение (серверный этап)

GET `/api/campaigns` возвращает `{campaigns: [...]}`: ID, имя, ruleset, массивы characters (id/name) и sessions (id). Порядок кампаний соответствует созданию. Журнал и личные заметки в список не включаются. Доступ локальный, а не разграниченный по пользователям.

POST `/api/campaigns` принимает `{mutationId, expectedRevision, state}` и **создаёт и сразу активирует** новую кампанию с одним персонажем и одной сессией. Нужен полный state формата 1, прошедший обычную проверку. Текущая игра не копируется автоматически; начальные данные должен явно подготовить клиент. Это пока не конструктор классов или пустой универсальный лист.

POST `/api/context/select` принимает `{mutationId, expectedRevision, context: {campaignId, characterId, sessionId}}`. Все три сущности должны существовать и относиться к одной кампании (иначе 404). Переключение восстанавливает сохранённое состояние выбранной игры, не меняя данные предыдущей. Даже выбор уже активной игры — новая ревизия. Создание отдельных дополнительных персонажей/сессий в существующей кампании пока не реализовано.

Обе команды требуют application/json и X-Skaz-Client: local-v1, проходят Host/Origin и лимит тела 512 КиБ. Успех — HTTP 200 с актуальным workspace и `affectedContext` (ID игры, затронутой командой). Некорректная структура — 400, состояние — 422, конфликт ревизии или ключа — 409.

Создание/переключение, общая ревизия, снимок прогресса, история и квитанция команды фиксируются одной транзакцией. Таблица context_changes хранит mutation_id, тип операции и ID до/после, без изменения раскладки v2. Повтор с тем же ключом и содержимым возвращает `replayed: true` и исходный affectedContext, но **текущее** состояние активной игры. Он не создаёт дубль и не переключает игру заново после последующих действий. Ключи общие с обычными сохранениями; повтор ключа для другой операции запрещён.

Каждое переключение увеличивает глобальную ревизию: старый черновик/вкладка не может сохранить прогресс другой игры даже после переключения туда и обратно. Не следует автоматически заменять expectedRevision в конфликтном запросе. Будущий интерфейс должен блокировать переключение при несохранённом черновике, сбрасывать локальную отмену прежней игры, загружать возвращённый workspace целиком и явно подтверждать перенос JSON в другую кампанию. Активная игра пока общая для всех вкладок этого локального сервера. История также общая; фильтр по кампании ещё не реализован.

## Проверки

Тестируется перенос всех полей из реальной структуры v1, сохранение истории и идемпотентных запросов, стабильность ID после открытия, переименование без смены ID, резервная копия v2, откат некорректной миграции, полный откат сохранения при ошибке записи сессии, запрет связей между кампаниями и неизменность посторонней кампании при обновлении активной. Дополнительные сущности для теста создаются только во временной базе.
