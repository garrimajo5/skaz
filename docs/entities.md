# Кампания, персонаж и сессия: хранение v2

При открытии базы v1 сервер переносит текущую игру в связанные таблицы и назначает UUID каждой сущности. Повторное открытие не меняет ID. Сервер поддерживает создание и переключение игр; интерфейс доступен по кнопке «Кампании». Модель механик по-прежнему ограничена демо-бардом.

| Сущность | Данные |
| --- | --- |
| campaigns | Название, заметки карты, состояния этапов заданий, ruleset=5e-2014 |
| characters | Имя, описание, хиты, золото, ячейки, вдохновение, концентрация, личные заметки; campaign_id |
| sessions | Журнал, принятые/пропущенные демонстрационные события и их правки; campaign_id |
| active_context | Выбор по умолчанию для клиентов без X-Skaz-View |
| browser_contexts | Выбор campaign_id, character_id, session_id для каждого view_id |

Составные внешние ключи не позволяют назначить в активную игру персонажа или сессию другой кампании. Это целостность связей, а не авторизация: пользователи, членство и видимость ещё не реализованы. У старых заметок нет достоверных сессий происхождения; личные заметки остаются у персонажа, текущий журнал переносится целиком в одну сессию. Время начала и номер сессии не выдумываются. Заголовки используют метаданные выбранной сессии; новые сессии требуют явных названия и даты.

## Совместимость и миграция

Версия **раскладки SQLite** хранится в workspace.schema_version и теперь равна 2. Версия **формата JSON/API** остаётся 1: существующие экспорты, клиент и черновики совместимы. Чтение `/api/workspace` собирает состояние из сущностей. `workspace.state_json` сохраняется как совместимый полный снимок выбора по умолчанию; основное чтение собирает состояние выбранного окна из сущностей. История `changes` не переписывается, старые ключи повторных запросов продолжают работать.

Миграция выполняется внутри BEGIN IMMEDIATE: проверка исходного состояния, создание таблиц, перенос и смена версии либо завершаются вместе, либо откатываются. Новый запуск сервера не следует совмещать с работающим старым процессом. Перед обновлением останови старый сервер и сделай SQLite backup старой версией. Откат на старый код требует восстановления копии базы v1: старый код не поддерживает раскладку v2. При восстановлении сохраняй также текущую v2, если после переноса уже были изменения.

Обычное сохранение атомарно обновляет сущности, общий снимок, ревизию и историю. Чтение использует один SQL-снимок для всех сущностей и ревизии. Современный JSON-импорт создаёт новую кампанию с новыми ID и сохраняет внутренние связи поддерживаемого формата. SQLite backup включает исходные ID, все кампании и полную историю; перенос активной игры ограничен её содержимым и версией экспорта. Каталог хранится независимо.

GET `/api/context` возвращает `revision`, `updatedAt`, `ruleset` и объекты `campaign`, `character`, `session`: каждый имеет `id` и `data`; персонаж и сессия также `campaignId`. Ответ GET `/api/workspace` дополнительно содержит `context: {campaignId, characterId, sessionId}`. Изменения ресурсов проходят через прежний PUT `/api/workspace`.

## Создание и переключение (серверный этап)

GET `/api/campaigns` возвращает `{campaigns: [...]}`: ID, имя, ruleset, массивы characters (id/name) и неархивных sessions (id). Порядок кампаний соответствует созданию. Журнал и личные заметки в список не включаются. Доступ локальный, а не разграниченный по пользователям.

POST `/api/campaigns` принимает `{mutationId, expectedRevision, state}` и **создаёт и сразу активирует** новую кампанию с одним персонажем и одной сессией. Нужен полный state формата 1, прошедший обычную проверку. Текущая игра не копируется автоматически; начальные данные должен явно подготовить клиент. Это пока не конструктор классов или пустой универсальный лист.

POST `/api/context/select` принимает `{mutationId, expectedRevision, context: {campaignId, characterId, sessionId}}`. Все три сущности должны существовать и относиться к одной кампании (иначе 404). Переключение восстанавливает сохранённое состояние выбранной игры, не меняя данные предыдущей. Даже выбор уже активной игры — новая ревизия. Следующая сессия создаётся отдельным API: см. sessions.md; дополнительные персонажи создаются через POST /api/characters из явного демо-шаблона. Архивные сессии доступны только для чтения.

Обе команды требуют application/json и X-Skaz-Client: local-v1, проходят Host/Origin и лимит тела 512 КиБ. Успех — HTTP 200 с актуальным workspace и `affectedContext` (ID игры, затронутой командой). Некорректная структура — 400, состояние — 422, конфликт ревизии или ключа — 409.

Создание/переключение, общая ревизия, снимок прогресса, история и квитанция команды фиксируются одной транзакцией. Таблица context_changes хранит mutation_id, тип операции и ID до/после, без изменения раскладки v2. Повтор с тем же ключом и содержимым возвращает `replayed: true` и исходный affectedContext, но **текущее** состояние активной игры. Он не создаёт дубль и не переключает игру заново после последующих действий. Ключи общие с обычными сохранениями; повтор ключа для другой операции запрещён.

Каждое переключение увеличивает глобальную ревизию: старый черновик/вкладка не может сохранить прогресс другой игры даже после переключения туда и обратно. Не следует автоматически заменять expectedRevision в конфликтном запросе. Интерфейс блокирует переключение при несохранённом черновике, сбрасывает локальную отмену прежней игры и загружает возвращённый workspace целиком. При современном импорте JSON создаётся новая кампания. Вкладки передают X-Skaz-View и независимо выбирают игру. Без заголовка используется прежний общий выбор; история пока общая, фильтр по кампании ещё не реализован.

## Проверки

Тестируется перенос всех полей из реальной структуры v1, сохранение истории и идемпотентных запросов, стабильность ID после открытия, переименование без смены ID, резервная копия v2, откат некорректной миграции, полный откат сохранения при ошибке записи сессии, запрет связей между кампаниями и неизменность посторонней кампании при обновлении активной. Дополнительные сущности для теста создаются только во временной базе.


## Независимый выбор окна (20.10.2026)

X-Skaz-View — 8–80 ASCII букв, цифр и дефисов; это случайный идентификатор выбора, не пользователь и не секрет доступа. Новое окно получает выбор по умолчанию, затем может переключиться независимо. Все методы чтения/изменения контекста используют привязанный к запросу объект; параллельные запросы не меняют глобальную переменную текущего героя. Сохранение требует общей ревизии, а квитанция scoped-запроса дополнительно связана с view_id. Повтор из другого окна получает конфликт.

Начало сессии архивирует прежнюю и переводит окна той же кампании/сессии в новую, сохраняя каждого героя. При возврате со старой версии кода архивные выборы восстанавливаются на последнюю неархивную сессию кампании. Новая таблица добавляется без удаления старой; число сохранённых окон ограничено 10 000, автоматической очистки пока нет.

Клиент хранит ID в sessionStorage и удерживает Web Lock, чтобы дублирование вкладки не копировало активную очередь команд. Без Web Locks дублированные вкладки могут разделить выбор. Общий вход VPS ещё не ограничивает доступ к чужим героям; для этого нужны отдельные аккаунты и серверные права. Подробный контракт: local-api.md.


20.10: `character_stats(character_id, stats_json)` хранит необязательные ручные значения, `character_stats_changes` — снимки до/после с отложенной внешней ссылкой на общий receipt. Таблицы добавочные, версия workspace и JSON state не меняются. Прежний релиз 70fbe57 проверен на синтетической базе: открывает её, меняет ресурсы, сохраняет новую таблицу для возвращённого нового кода. При откате старый UI не показывает ручные статистики и его JSON не переносит их; для сохранности использовать SQLite backup и вернуться к новому коду. Не считать старый JSON полной копией ручного листа. Удаление таблиц при откате не требуется.


Ручной лист героя хранится отдельно в character_sheets: происхождение, название класса/сочетания и подкласса, общий уровень, до 20 именованных счётчиков со стабильными ID. Это ручные данные D&D 2014, без автоматического конструктора/восстановления. character_sheet_changes сохраняет до/после в одной транзакции с changes; полный SQLite backup сохраняет их. JSON v9 переносит текущие значения выбранного героя, остальные герои/аудит в JSON не входят. Предыдущий код сохраняет добавочные таблицы, но его UI/JSON не показывает собственный класс: для отката и последующего переноса нужна полная копия.
