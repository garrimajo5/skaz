# Кампания, персонаж и сессия: хранение v2

Реализован первый этап разделения прогресса. При открытии базы v1 сервер переносит текущую игру в связанные таблицы и назначает UUID каждой сущности. Повторное открытие не меняет ID. Создание нескольких игр и переключение через API/интерфейс пока не доступны; это следующий этап. Модель механик по-прежнему ограничена демо-бардом.

| Сущность | Данные |
| --- | --- |
| campaigns | Название, заметки карты, состояния этапов заданий, ruleset=5e-2014 |
| characters | Имя, описание, хиты, золото, ячейки, вдохновение, концентрация, личные заметки; campaign_id |
| sessions | Журнал, принятые/пропущенные демонстрационные события и их правки; campaign_id |
| active_context | Активные campaign_id, character_id, session_id |

Составные внешние ключи не позволяют назначить в активную игру персонажа или сессию другой кампании. Это целостность связей, а не авторизация: пользователи, членство и видимость ещё не реализованы. У старых заметок нет достоверных сессий происхождения; личные заметки остаются у персонажа, текущий журнал переносится целиком в одну сессию. Время начала и номер сессии не выдумываются. Заголовки демо-сессии в клиенте пока фиксированы.

## Совместимость и миграция

Версия **раскладки SQLite** хранится в workspace.schema_version и теперь равна 2. Версия **формата JSON/API** остаётся 1: существующие экспорты, клиент и черновики совместимы. Чтение `/api/workspace` собирает состояние из сущностей. `workspace.state_json` сохраняется как совместимый полный снимок последнего подтверждённого состояния; основное чтение не использует его. История `changes` не переписывается, старые ключи повторных запросов продолжают работать.

Миграция выполняется внутри BEGIN IMMEDIATE: проверка исходного состояния, создание таблиц, перенос и смена версии либо завершаются вместе, либо откатываются. Новый запуск сервера не следует совмещать с работающим старым процессом. Перед обновлением останови старый сервер и сделай SQLite backup старой версией. Откат на старый код требует восстановления копии базы v1: старый код не поддерживает раскладку v2. При восстановлении сохраняй также текущую v2, если после переноса уже были изменения.

Обычное сохранение атомарно обновляет сущности, общий снимок, ревизию и историю. Чтение использует один SQL-снимок для всех сущностей и ревизии. Локальный JSON-импорт заменяет содержимое текущей игры с сохранением её ID. SQLite backup включает ID и связи; JSON-экспорт прогресса их не переносит. Каталог хранится независимо.

GET `/api/context` возвращает `revision`, `updatedAt`, `ruleset` и объекты `campaign`, `character`, `session`: каждый имеет `id` и `data`; персонаж и сессия также `campaignId`. Это чтение активной игры для будущего интерфейса. Записи и переключения через этот путь нет; изменения пока проходят через прежний PUT `/api/workspace`.

## Проверки

Тестируется перенос всех полей из реальной структуры v1, сохранение истории и идемпотентных запросов, стабильность ID после открытия, переименование без смены ID, резервная копия v2, откат некорректной миграции, полный откат сохранения при ошибке записи сессии, запрет связей между кампаниями и неизменность посторонней кампании при обновлении активной. Дополнительные сущности для теста создаются только во временной базе.
