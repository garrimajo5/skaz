# Серверная модель индивидуального доступа

Статус 20.10.2026: экспериментальная серверная основа реализована и проверяется тестами. На VPS по-прежнему общий вход Nginx; индивидуальная авторизация и интерфейс управления участниками ещё не подключены. Наличие таблиц не меняет права посетителей текущего приложения.

## Граница доверия

`openStore().access` — административный интерфейс, не HTTP API. Миграция добавляет пользователей, членство owner/gm/player, явные разрешения на героев, окна пользователя, журнал команд доступа и авторов изменений. Существующие игры не получают владельца автоматически. Паролей или токенов в этой модели нет.

`forUser(userId, viewId)` выдаёт только чтение после проверки личности доверенным вызывающим кодом. Одинаковые ID окна у двух пользователей преобразуются в разные серверные контексты. Каждое чтение проверяет текущие разрешения; отзыв прав не переключает окно молча на другого героя. Экспорт и обзор сессии читаются согласованно; каталог ограничен точными встроенными карточками, одного поля лицензии недостаточно.

`forUser(userId, viewId, {write:true})` — экспериментальная возможность записи. Игрок меняет своего героя, личные события, книгу и инвентарь. Общие журнал, задания, места и сессии меняют owner/gm. Даже мастер не получает личный лист другого игрока без явного разрешения. Создание новой кампании и импорт присваивают владельца и героя в той же транзакции. Создание дополнительного героя доступно owner/gm и выдаёт доступ создателю; выдача доступа другому участнику остаётся административной.

Проверки выполняются внутри транзакции изменения и повторно для сохранённых квитанций. История ограничена собственными изменениями доступного выбранного героя; история старого общего режима не раскрывается. Отмена инвентаря разрешена только автору последней подходящей операции. Отказ записи журнала автора откатывает также новую игру и разрешения.

`createApp(store,{authenticate})` принимает только доверенную серверную функцию, возвращающую проверенный userId. По умолчанию этот экспериментальный HTTP-режим закрывает запись; отдельный boolean-флаг individualWrites:true включает проверяемые изменения только вместе с authenticate. Пустая личность даёт 401 без возврата к общему доступу. Заголовки user_id, X-Skaz-View и query-параметры не являются удостоверением личности. `server/index.mjs` этот режим не включает.

## Администрирование и резервная копия

Сначала подготовить JSON-команду вне Git, затем выполнить:

```sh
node scripts/access-admin.mjs /path/existing.sqlite /private/command.json /private/new-backup.sqlite
```

Команда требует существующую базу и новый отдельный путь копии. SQLite backup создаётся до миграции и изменения доступа; существующая копия не перезаписывается. Файл получает права 0600 на POSIX. При ошибке назначения копия сохраняется, транзакция отменяется. Файлы команд и резервов содержат приватные идентификаторы и не отправляются в Git.

Поля команд (ID: 8–80 латинских букв, цифр или дефисов):

| action | Дополнительные обязательные поля |
|---|---|
| create-user | userId, displayName |
| bootstrap-owner | userId, displayName, campaignId, characterId |
| set-member | userId, campaignId, role: owner/gm/player |
| remove-member | userId, campaignId |
| grant-character / revoke-character | userId, campaignId, characterId |
| set-enabled | userId, enabled: boolean |

Последнего активного владельца нельзя отключить, удалить из кампании или понизить до назначения другого активного владельца. Разрешение на героя требует членства в его кампании; удаление членства удаляет разрешения. Журнал фиксирует действие, цель и время, но пока не полную историю значений ролей.

## Ограничения и следующий этап

Экспериментальные форма входа, пароли и серверные сеансы описаны в authentication.md. Приглашений, восстановления доступа и публичной регистрации пока нет. Общая ревизия остаётся общей для базы. Для вошедшего игрока без героя есть экран ожидания назначения; общего персонажа он не получает. Личные импортированные карточки не имеют владельца: их общий поиск и экспорт в индивидуальном режиме запрещены, сохранённые карточки в разрешённом личном листе читаются. Импорт новой игры в этом режиме допускает только точные встроенные карточки. Секретные материалы мастера и общий поток предложений всех игроков не реализованы.

Следующий ограниченный этап: интерфейс участников и полноценная проверка входа двух пользователей браузером через HTTPS перед безопасной миграцией общего доступа. До этого не включать экспериментальную модель на рабочем VPS и не выдавать её за готовую многопользовательскую версию.


Обновление 20.10: реализован экспериментальный [индивидуальный вход](authentication.md), серверный отзыв сессий и разделение клиентских черновиков. Рабочий entry point и VPS пока сохраняют общий вход; UI назначения участников и полная HTTPS-проверка ещё впереди.

## Права в интерфейсе

Индивидуальный GET /api/workspace и ответы команд с состоянием содержат permissions: mode=individual, роль и булевы character/shared/manageCampaign/catalog/newCampaign/select/import/history/export. Это подсказки интерфейсу: сервер по-прежнему проверяет актуальные права внутри транзакции. При смене роли без изменения игровой ревизии открытая вкладка просит обновиться.

Игрок изменяет личный лист и заметки. Запись расхода ресурса попадает в личные заметки; раньше она пыталась изменить общий журнал и отклонялась. Мастер/владелец меняет общие задания, карту, сюжет и сессии. Изменение названия кампании недоступно игроку в форме профиля. Управление общим каталогом в индивидуальном режиме пока доступно только администратору вне UI. Режим чтения оставляет поиск, чтение и экспорт; редакторы отмечены как недоступные. После отклонения команды по правам черновик остаётся для скачивания, повтор заблокирован, можно загрузить актуальную игру. Он не превращается в сохранённую запись.

Локальный браузерный сценарий использовал отдельную синтетическую базу и доверенный тестовый адаптер: урон игрока, личное предложение и подтверждение, общие задания только для чтения, смена роли и отметка этапа мастером. Это проверка прав в UX, не реального браузерного cookie-входа. Снимок docs/design/player-permissions-polaris.png.

Дополнительно tests/https-auth.test.mjs проверяет настоящий TLS-прокси только на loopback, одноразовый сертификат с явным доверием тестового клиента, отказ без доверия, cookie/Origin/выход, два отдельных листа и старую вкладку после смены аккаунта. OpenSSL нужен для теста, доверие устройства не меняется. Это программная проверка HTTPS, не физический планшет или настоящий браузерный вход.

Попытка временного публичного HTTPS-стенда на 8443 отклонена автоматической проверкой разрешений: текущую авторизацию на VPS она не сочла разрешением на такое сетевое открытие. Команда не выполнялась; отдельной проверкой подтверждены отсутствие конфигурации/каталога стенда и закрытый порт. Взамен выполнены локальные проверки; новых публичных портов нет.

В этом этапе дополнительно устранён первоначальный показ демо-персонажа до ответа сервера. Пока личность/права и сохранённый лист не загружены, показан экран загрузки; ошибка не открывает демо как сохранённую игру. Повторная успешная загрузка восстанавливает обычный интерфейс. Режим чтения проверен браузером: текст и источник личного заклинания доступны, отметка и сохранение отключены.
