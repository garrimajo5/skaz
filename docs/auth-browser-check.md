# Проверка индивидуального входа до миграции

Это отдельная синтетическая игра, а не включение ролей в рабочей базе. Полная
проверка браузером через доверенный HTTPS пока остаётся критерием готовности.
Программная проверка TLS и локальные формы её не заменяют.

## Подготовка без открытия доступа

Node 24, существующий приватный родительский каталог, без npm-зависимостей:

```sh
node scripts/auth-fixture.mjs prepare data/auth-check-NEW https://__PUBLIC_HOST__:8443
node scripts/auth-fixture.mjs serve data/auth-check-NEW 4177
```

`prepare` принимает только **новый** каталог. Он создаёт собственную SQLite,
двух героев из явно демонстрационного шаблона и три аккаунта: владелец со своим
героем, игрок с другим личным героем, пользователь без назначения. Существующие
игры, назначения и конфигурация запуска не читаются и не меняются. Случайные
пароли находятся только в `skaz-fixture-credentials.json`, не в выводе команды.
Этот файл исключён из Git дополнительно; весь стенд хранить в игнорируемом
`data/` или вне репозитория. В Linux каталог имеет 0700, SQLite и JSON — 0600;
в Windows нужна соответствующая приватность каталога средствами системы.

`serve` сверяет маркер базы и три тестовых ID, отвергает постороннюю SQLite и
символьную ссылку вместо файла. Слушает только IPv4 loopback. Путь рабочей базы,
переменные SKAZ_DB и обычный entry point не используются. Частично подготовленный
каталог без завершающего манифеста не запускается; для повтора нужен новый каталог.
Проверка не меняет доверенные сертификаты устройства и не отключает проверку TLS.

Шаблон `deploy/nginx-auth-check.conf.example` использует существующий доверенный
сертификат, внешний общий пароль и отдельный upstream 127.0.0.1:4177. Он привязан
к **127.0.0.1:8443**, по умолчанию снаружи недоступен и автоматически не
устанавливается. Рабочий HTTPS на 443 и его SQLite остаются прежними.
Перед временной конфигурацией сохранить backup и точный путь возврата,
проверить nginx -t, после проверки убрать конфигурацию и остановить стенд.

20.10 пользователь отдельно разрешил временный внешний тест на 8443. Он
выполнен, затем автоматическое закрытие удалило конфигурацию и правило firewall;
отсутствие слушателей 4177/8443 подтверждено. Скрипт по-прежнему сам не открывает
внешний порт. Не заменять рабочую базу тестовой и не снимать общий вход ради
проверки. Для будущего повторного открытия заново согласовать срок доступа.

При двух уровнях входа браузер может сбросить HTTP Basic после ответа 401 от
индивидуальной формы. Тестовый шаблон переводит отказ только /api/auth/login
в JSON 403 с той же общей ошибкой, сохраняя внешний пароль и проверку сеанса.
401 остальных API остаются 401. Проверено: неверный пароль → сообщение →
правильный пароль → личный лист, без повторного запроса Basic. Это специальная
конфигурация стенда, не изменение рабочего Nginx на 443.

## Браузерный сценарий

Использовать отдельные профили браузера для независимых посетителей; разные
вкладки одного профиля намеренно делят cookie и при смене аккаунта блокируют
старый интерфейс. Это ожидаемая защита, не проверка независимости пользователей.

1. Без общего пароля Nginx не открывает страницы и API. После общего входа
   появляется индивидуальная форма. Неверный пароль не раскрывает существование
   аккаунта; отсутствие связи позволяет повторить ввод без сохранения пароля.
2. Владелец видит своего героя и «Участники». Игрок видит только отдельного героя,
   личные записи и книгу; общие задания/карта доступны для чтения. Проверить
   отсутствие чужого героя в выборе, истории и JSON-экспорте.
3. Войти без назначения: экран ожидания показывает только код и выход. Добавить
   этого существующего участника владельцем. Одного членства недостаточно:
   лист появляется только после отдельного подтверждённого разрешения.
4. Отозвать лист. Уже открытая вкладка скрывает старый интерфейс при следующем
   запросе; повтор команды/история/экспорт не возвращают отозванные данные.
   Понижение роли убирает общую запись. Проверить обновление вкладки.
5. Два окна одного профиля: выйти/войти другим аккаунтом в соседнем окне.
   Старое окно блокируется; его черновик не отправляется от нового пользователя.
   Проверить возвращение страницы кнопкой «Назад» и ответ запроса в полёте.
6. Выход отзывает сеанс. Перезагрузка и повтор cookie не открывают прежний лист.
   Проверить Полярис, Уголь и Атлас на размерах планшета и узком экране.

Зафиксировать реальные результаты, ошибки и размеры, затем закрыть тестовые
вкладки, остановить процесс, убрать временный прокси и подтвердить закрытие
слушателей. Синтетические аккаунты не переносятся в рабочую базу. Перед миграцией
всё равно нужны согласованные пользователем реальные назначения и проверенное
восстановление. `access-readiness` удостоверяет только структуру данных, не это
решение и не успешность браузерного сценария.

## Фактический результат 20.10

Один профиль встроенного Chromium, доверенный HTTPS без обхода предупреждений.
Последовательно проверены владелец и игрок с разными героями, отсутствие чужого
героя в выборе игрока, недоступность общих изменений, отсутствие «Участники» у
игрока, выход и блокировка второго окна. Без назначения показан экран ожидания,
владелец подтвердил добавление аккаунта и отдельное разрешение на лист; после
нового входа лист появился. Административный отзыв синтетического разрешения
скрыл уже открытый лист при проверке обновлений; повторное открытие показало
ожидание. Выход вернул форму входа. Полярис, Атлас и Уголь просмотрены.

Размер viewport-инструмента фактически не применился: innerWidth остался 1280,
снимки 1280×720. Узкий/планшетный размер в этом HTTPS-этапе **не засчитан**.
Отдельных независимых профилей в доступном браузере нет; одновременные cookie
разных пользователей подтверждаются программными тестами, не этим браузером.
Back/forward cache, поздние ответы и отсутствие утечек JSON/истории проверяются
регрессиями; новых браузерных подтверждений этих сценариев здесь не получено.
Приложение не объявляется готовым к открытой регистрации/многопользовательскому
размещению; остаются назначения, дополнительные профили и реальные устройства.
