# Локальный API 0.2

Актуально 20.10: настройки используют перенос v9, поддержан импорт v1–v9. Выбор игры независим для вкладок (см. последний раздел). Ниже сохранена история развития контрактов v2–v5; фразы «пока» в этих разделах описывают соответствующий этап. Текущий интерфейс описан в README и последних разделах этого файла.

Серверный каталог: GET `/api/catalog` и `/api/catalog/coverage`, локальный импорт — см. [формат и ограничения](catalog.md). Каталог хранится отдельно от JSON прогресса.

Node.js 24+, SQLite. Один локальный пользователь, несколько кампаний с персонажами из демо-шаблона и несколькими сессиями. Авторизации и доступа по LAN в этой версии нет. Слушает только loopback; Host и Origin проверяются. Статический сервер выдаёт только явно перечисленные файлы клиента, не базу и не исходники сервера.

## Методы

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/health` | Режим и тип хранилища |
| GET | `/api/workspace` | `schemaVersion`, `revision`, `updatedAt`, `state` |
| GET | `/api/context` | Активные кампания, персонаж и сессия с ID, данными и общей ревизией |
| GET | `/api/campaigns` | Список кампаний и ID их персонажей/сессий |
| POST | `/api/campaigns` | Создать и активировать кампанию из явно переданного state |
| POST | `/api/context/select` | Выбрать кампанию, персонажа и сессию с проверкой общей ревизии |
| POST | `/api/sessions` | Начать следующую сессию активной кампании, архивируя прежнюю |
| GET | `/api/campaigns/{id}/sessions` | Все сессии кампании и метаданные |
| GET | `/api/sessions/{id}` | Журнал сессии и метаданные без переключения игры |
| PUT | `/api/workspace` | Проверка и транзакционное сохранение состояния |
| GET | `/api/history` | Последние 50 изменений без полных снимков |
| GET | `/api/export` | JSON прогресса для переноса |

PUT требует `Content-Type: application/json` и `X-Skaz-Client: local-v1`. Этот заголовок защищает от простых запросов постороннего сайта, но не является авторизацией. Тело:

```json
{
  "mutationId": "уникальный-uuid",
  "expectedRevision": 0,
  "label": "Здоровье восстановлено",
  "state": {}
}
```

`state` в примере сокращён: сервер требует полную структуру из `server/state.mjs`. Тема — локальная настройка браузера и в серверный прогресс не входит. Максимум тела 512 КиБ. Неверные поля или ресурсы возвращают 422; старая версия — 409. Повтор идентичного `mutationId` не создаёт новое изменение, а возвращает актуальное состояние; повтор того же ID с другим содержимым — 409.

В транзакции записываются состояние, версия и запись истории с предыдущим и следующим снимком. Отмена — новое сохранение предыдущего состояния с проверкой версии. Запрос со старой версией не может затереть чужое изменение. Автоматического слияния пока нет.

## Хранение

Начало сессии и чтение архива описаны в [контракте сессий](sessions.md). Архив нельзя активировать для редактирования. Кнопка «Сессии» открывает начало сессии и просмотр журнала/архива. Ответ workspace дополнен полем session с name и playedOn; они могут быть null для прежних сессий.

`data/skaz.sqlite`, путь можно переопределить через `SKAZ_DB`. Раскладка базы v2: `campaigns`, `characters`, `sessions`, `active_context` хранят связанные сущности; `workspace` — ревизию и совместимый снимок; `changes` — историю и ключи повторов. Каталог хранится отдельно. API и JSON-экспорт сохраняют schemaVersion=1. Чтение собирает прогресс из сущностей; все изменения выполняются в общей транзакции. Подробности и условия обновления — [хранение сущностей](entities.md). Создание и переключение игр доступны в API и кнопке «Кампании»; пользователи ещё не реализованы. До многопользовательского режима нужны серверные команды игровых действий вместо передачи полного состояния. Проверка структуры и пределов ресурсов не заменяет полный движок правил D&D.

История снимков растёт вместе с журналом; архивирование пока не реализовано. Рекомендуется регулярно делать резервные копии. `node scripts/backup.mjs` использует SQLite backup API, который корректно снимает копию работающей базы, включая подтверждённые записи при WAL.

## Поведение клиента при сбое

Клиент не показывает успешное сохранение до ответа сервера. Если запрос завершился ошибкой, кандидат остаётся локальным черновиком с прежним `mutationId`. До разрешения сбоя новые изменения блокируются. Повтор запроса безопасен даже если первый ответ потерялся после успешной записи.

Черновики разных вкладок имеют разные ключи; после перезагрузки вкладка находит собственный черновик. Черновики закрытых вкладок доступны в «Данные и настройки → Несохранённые черновики». Их можно скачать и затем импортировать. При конфликте можно скачать свой вариант и явно загрузить актуальное состояние. Автоматического фонового объединения и realtime-обновления других вкладок нет.

Самостоятельный `dist/skaz.html`, открытый через `file:`, остаётся демо в браузере. Серверное приложение запускается отдельно по HTTP. Старое сохранение можно перенести вручную через настройки, если оно доступно на том же origin; файл из другого браузера переносится экспортом и импортом.

Каталог поддерживает необязательную структуру `spell` и режим источника `cc-by-4.0` с обязательными `attribution`/`changes`. Отчёт `/api/catalog/coverage` дополнен `openlyLicensed` и `structuredSpells`. Контракт и ограничения: [catalog.md](catalog.md).

Для kind=item поддерживается необязательная структура `item`: тип, редкость, настройка и формула лечения зелья. `/api/catalog/coverage` дополнен `structuredItems`. Импорт не меняет ресурсы персонажа.

Для kind=monster доступна необязательная структура `monster` с основными характеристиками; `/api/catalog/coverage` дополнен `structuredMonsters`. Дробная опасность хранится строкой (например, `1/4`). Контракт: [catalog.md](catalog.md).

Для kind=mechanic поддерживается необязательное `mechanic: { category: "condition", effects: [...] }`. Coverage дополнен `structuredMechanics`. Ссылки `links` проверяются на наличие целей; применение состояний к персонажу не реализовано.

Для kind=artifact поддерживается необязательное `artifact` с типом, настройкой и максимумом/описанием восстановления зарядов. Coverage дополнен `structuredArtifacts`. Текущий запас зарядов экземпляра в каталоге не хранится.


## Инвентарь: серверный этап

GET `/api/inventory` возвращает `revision`, `context` активной игры и `entries`: `{catalogId, quantity, entry}`. `entry` — снимок записи каталога при первом добавлении, включая источник. Список относится только к активному персонажу.

POST `/api/inventory` требует обычные локальные защитные заголовки и тело:

```json
{"mutationId":"unique-mutation-id","expectedRevision":0,"characterId":"active-character-id","catalogId":"srd51:2014:item:potion-of-healing","quantity":2}
```

Количество — целое 1–999, суммарно на вид предмета не более 999, до 1000 видов у персонажа. Допустимы только item/artifact редакции 2014, уже существующие в каталоге. Для справочных ссылок не подразумевается наличие полных характеристик. Несовпадение активного персонажа или ревизии — 409; отсутствующий материал — 404; неверные значения/категория — 422. Неизвестные поля команды — 400.

Ответ POST — обычный workspace и affectedContext; список нужно читать GET. Идентичный повтор возвращает актуальную игру и первоначальный affectedContext, не переключает персонажа и не увеличивает количество снова. Золото не списывается: это добавление имущества, не покупка. Здоровье, бонусы и настройки предметов не меняются.

Таблицы inventory и inventory_changes добавляются без преобразования старого state. Инвентарь связан с персонажем, не с сессией. Общая ревизия/история/квитанция и отдельные снимки инвентаря записываются атомарно. Старые сохранения листа не заменяют инвентарь. SQLite backup включает всё. **JSON экспорта/импорта прогресса v1 пока не включает и не восстанавливает инвентарь**; до отдельного формата переноса используйте SQLite backup. Автоматического преобразования нарисованных демо-предметов нет.

Уменьшение количества доступно через серверную команду ниже; экипировка, индивидуальные заряды и применение эффектов зелий пока не реализованы. Количество пока группируется по ID каталога, отдельные экземпляры артефактов не моделируются.

Клиент: «Герой → Инвентарь → Открыть» читает список, карточка предмета/артефакта в справочнике открывает форму количества с именем персонажа и кампании. Команда добавления использует общую сохраняемую очередь: повтор после сбоя/перезагрузки сохраняет mutationId, characterId и expectedRevision. Конфликт блокирует новые изменения до явного обновления. Чтение инвентаря другой ревизии не принимает её молча. JSON v1 не заменяет инвентарь; ограничение указано в настройках.


### Списание количества (сервер)

POST `/api/inventory/remove` принимает те же поля и защитные заголовки, что добавление: `mutationId`, `expectedRevision`, `characterId`, `catalogId`, `quantity`. Количество — положительное целое 1–999, не больше остатка. При полном списании строка исчезает из текущего списка, а прежний снимок с источником остаётся в истории. Это учёт потери, передачи или расхода имущества: лечение, золото и другие ресурсы не меняются.

Отсутствующая строка инвентаря — 404; недостаточный остаток или неверное количество — 422; чужой активный персонаж, старая ревизия или повтор ключа с другой командой — 409. Ключ добавления нельзя использовать для списания. Одинаковый повтор списания не выполняется снова, даже после полного расходования или смены игры; ответ содержит актуальный workspace и первоначальный affectedContext. Списание, ревизия и история атомарны. Ошибка записи истории откатывает даже полное удаление строки. Серверная отмена описана ниже; списание и отмена доступны в окне инвентаря.


### Отмена последней операции инвентаря (сервер)

POST `/api/inventory/undo` с обычными защитными заголовками принимает `{mutationId, expectedRevision, characterId, targetMutationId}`. Все поля обязательны. targetMutationId — ID добавления или списания. Отменяется только последняя операция всей игры: её ревизия должна совпадать с текущей, персонаж — с активным, а инвентарь — с сохранённым результатом исходной операции. Любое последующее сохранение, переключение игры или начало сессии закрывает возможность отмены. Это намеренное ограничение первой версии.

Сервер восстанавливает предыдущий снимок инвентаря вместе с происхождением предметов, создаёт новую ревизию и запись истории, не меняя остальные ресурсы. Неизвестная операция — 404, неверный ID — 422, лишние поля — 400; устаревшая/чужая операция или попытка отменить отмену — 409. Идентичный повтор с тем же mutationId возвращает актуальную игру и первоначальный affectedContext без повторного восстановления. Новый ключ не позволяет отменить ту же операцию второй раз. При сбое истории восстановление откатывается целиком. Кнопки списания и отмены подключены к сохраняемой очереди клиента: после сбоя и перезагрузки отправляется прежняя команда с тем же ключом.


GET /api/inventory дополнен `undo: {mutationId, label} | null`. Сервер возвращает доступную последнюю операцию добавления/списания для активного персонажа. После любого последующего изменения игры или отмены поле равно null. Клиент показывает кнопку отмены по этому полю, в том числе после перезагрузки. Проверка ревизии и исходной операции всё равно выполняется сервером при POST.


### Экспорт активной игры v2 (серверный этап)

GET `/api/export/active` отдаёт скачиваемый `skaz-active-v2.json` без кэширования. Формат: `app: "skaz-active"`, `schemaVersion: 2`, `ruleset: "5e-2014"`, `scope: "active-game"`, `exportedAt`, `source: {revision, context}`, `state`, `session: {name, playedOn}`, `inventory: [{catalogId, quantity}]`, `catalog: {schemaVersion: 1, entries: [...]}`. Источники предметов включены в записи каталога без изменений. В каталог входят только предметы инвентаря и все достижимые связи links, включая транзитивные; циклы не создают дублей. Пустой инвентарь даёт пустой каталог.

Экспорт читает данные в одной транзакции, не меняет ревизию и историю. Отсутствующая зависимость или несовпадение снимка предмета с каталогом возвращает 409 вместо неполного файла. source.context — сведения об исходной игре, не команда переключения на неё.

Охват: активный персонаж, данные активной кампании и текущей сессии, инвентарь с необходимыми материалами. Архивы сессий, другие персонажи/кампании и история изменений не входят; для полной резервной копии остаётся SQLite backup. Старый GET /api/export и отдельная кнопка экспорта без инвентаря сохраняют v1. **Импорт v2 описан ниже и доступен в настройках с предпросмотром**. Новый файл нельзя восстановить существующим импортом v1.


### Импорт активной игры v2 (серверный этап)

POST `/api/import/active` требует локальные защитные заголовки и `{mutationId, expectedRevision, destination: "new-campaign", file: <экспорт v2>}`. Создаёт и активирует новую кампанию, персонажа и сессию с новыми ID. Существующие игры не заменяются. Исходные ID и дата экспорта проверяются как метаданные, но не управляют назначением. Ресурсы, текущий журнал, метаданные сессии (включая null), инвентарь и источники переносятся; архивы и история из исходной базы отсутствуют в формате.

Проверяются точные поля, редакция 2014, состояние, дата/название сессии, структура каталога, уникальные ID, числовые поля, количества 1–999, до 1000 видов предметов и до 1000 записей каталога. Каждая связь должна находиться внутри файла. Совпадающие записи существующего каталога используются повторно; конфликт содержимого под тем же ID даёт 409 без перезаписи. Новые материалы, игра, инвентарь, общая ревизия и история записываются одной транзакцией. Повтор той же нормализованной команды возвращает актуальную игру и первоначальный affectedContext, не создаёт ещё одну кампанию. Импорт не доступен для отмены инвентаря.

HTTP-лимит тела пока 512 КиБ, как у остальных команд; большие экспорты нужно переносить SQLite backup до расширения механизма. Формат v2 не является полной копией базы. В настройках доступны скачивание v2 и предпросмотр импорта с явным созданием новой кампании.

Клиент перед отправкой проверяет размер сериализованной команды целиком (512 КиБ), включая служебные поля. Импорт сохраняется в очереди с прежним ключом при сбое/перезагрузке. Экспорт v2 читает серверный снимок и отказывается скачивать его при несовпадении контекста или ревизии с открытой игрой.


### Список заклинаний персонажа (серверный этап)

GET `/api/spellbook` возвращает `{revision, context, entries: [{catalogId, status, entry}]}`. POST на тот же путь с локальными защитными заголовками принимает `{mutationId, expectedRevision, characterId, catalogId, status}`. status: `known` (изучено), `prepared` (подготовлено) или `remove` (убрать из списка). Это ручные отметки игрока, а не проверка правил класса: доступность заклинания, лимиты подготовки и допустимый уровень пока не вычисляются. Допустимы только записи spell редакции 2014, включая справочные ссылки; снимок сохраняет источник первого добавления. Максимум 1000 записей у персонажа.

Изменение статуса не расходует ячейки, не меняет концентрацию, хиты или журнал. Список сохраняется при обычном сохранении и начале сессии, изолирован по персонажу. Нет строки при remove — 404, неверная категория/статус — 422, устаревшая ревизия/чужой активный персонаж — 409. История, список и ревизия атомарны; повтор безопасен после перезапуска и переключения игры. Таблицы character_spells и spell_changes добавляются без изменения старых данных.

В интерфейсе магии сохранённый список каталога открывается отдельной кнопкой; ниже остаются восемь демо-заклинаний. JSON v1/v2 не включает этот список; серверный формат v3 и SQLite backup включают его. known/prepared — взаимоисключающие отметки одной записи, переход между ними не создаёт дубль.


### Перенос списка заклинаний: v3

GET `/api/export/active-v3` возвращает `skaz-active-v3.json`: тот же контракт активной игры, но schemaVersion=3 и обязательное `spellbook: [{catalogId, status}]`. Статусы known/prepared; снимки источников и все достижимые связи входят в общий catalog. Каталог включает объединение материалов инвентаря и заклинаний без дублей. Старый экспорт v2 возвращает 409 при непустом серверном списке заклинаний, чтобы не потерять его незаметно.

POST `/api/import/active` принимает v2 и v3. В v3 проверяются наличие списка, не более 1000 записей, уникальность, статус и категория spell. Записи и история заклинаний входят в общую транзакцию импорта. V2 создаёт игру с пустым списком; нормализованный запрос v2 не изменён, чтобы сохранить совместимость уже записанных ключей повторов. HTTP-лимит 512 КиБ остаётся общим.

Настройки экспортируют v3 и принимают v1/v2/v3. Предпросмотр v3 показывает число заклинаний, а для v2 явно сообщает об их отсутствии. В v3 отсутствие списка отклоняется до подтверждения. Карточки заклинаний справочника открывают форму ручной отметки, список персонажа — просмотр и изменение/удаление. Команды проходят через сохраняемую очередь и повторяются с тем же ключом при сбое.


### Задания кампании (серверный этап)

GET `/api/quests` возвращает `{revision, context, quests}` активной кампании. Задание: `{id, campaignId, createdSessionId, title, description, status, steps}`. POST с обычными защитными заголовками принимает `{mutationId, expectedRevision, campaignId, questId, operation, quest}`; operation=create/update, quest содержит ровно `{title, description, status, steps}`. Клиент задаёт постоянный questId (8–80 латинских букв/цифр/дефисов). При создании сервер связывает задание с текущей сессией; последующее редактирование эту связь не меняет.

Название 1–200 символов, описание до 12000, статус active/completed/failed. До 50 этапов `{id,title,done}` с уникальным ID, непустым заголовком до 500 символов и булевым done; до 1000 заданий в кампании. Статус задания не выводится автоматически из этапов, награды и ресурсы не начисляются. Сохраняется порядок этапов. Удаления пока нет.

Старая ревизия, чужая активная кампания или занятый ID при создании дают 409; update отсутствующего/чужого задания — 404; неверные поля — 422. Запись, общая ревизия и quest_changes атомарны. Повтор не создаёт дубль и возвращает исходный affectedContext даже после смены игры. Обычное сохранение и новая сессия задания не заменяют.

Интерфейс пока показывает прежние демо-задания; новая модель не преобразует их автоматически. Перенос JSON v1/v2/v3 пока не содержит новые задания; SQLite backup содержит. До подключения UI следующий этап — перенос заданий с новыми ID и корректной связью с импортируемой сессией.


### Перенос заданий: v4 (серверный этап)

GET `/api/export/active-v4` возвращает `skaz-active-v4.json`: контракт v3 с schemaVersion=4 и обязательным `quests: [{origin, quest}]`. quest содержит title, description, status, steps по правилам POST /api/quests. origin содержит исходные campaignId, questId, sessionId. Экспорт включает все задания активной кампании, в том числе созданные в архивных сессиях. Сами архивные журналы не включаются. Порядок заданий/этапов сохраняется. Пустой список обязателен; максимум 1000 заданий. Повтор исходной пары campaignId/questId, неверные поля, ID, статусы и этапы отклоняются (422).

POST `/api/import/active` принимает v4 с прежним destination=new-campaign. Задания получают новые UUID; createdSessionId указывает на локальную сессию импорта. Это время появления записи в новой базе, а не утверждение о том, в какой сессии произошло событие. Исходные ID сохраняются отдельно в quest_origins; GET /api/quests для импортированного задания дополнительно возвращает `importedFrom: {campaignId, questId, sessionId}`. Эти сведения заявлены файлом, не являются внешними ключами и не дают доступа к исходной игре. Исходная сессия может отсутствовать в новой базе. Повторный экспорт сохраняет первоначальное происхождение, редактирование его не меняет. ID этапов сохраняются внутри нового задания.

Создание кампании, заданий, происхождения, инвентаря, заклинаний, каталога и общей записи импорта атомарно. Общая история фиксирует операцию import-active; отдельные quest_changes возникают при последующих редактированиях. Повтор ключа импорта после перезапуска не создаёт дубли. Старые нормализованные команды v2/v3 сохранены. Экспорт v2/v3 при непустом списке заданий возвращает 409 с подсказкой использовать v4 или SQLite backup. Legacy v1 остаётся ограниченным экспортом прогресса без этих сущностей.

HTTP-лимит 512 КиБ сохраняется. Клиент настроек пока экспортирует v3, принимает v1/v2/v3; v4 пока доступен только через API. Изменений интерфейса в этом этапе нет.


### Перенос v4 в настройках

Клиент экспортирует v4 и принимает v1/v2/v3/v4. Предпросмотр показывает число заданий и объясняет сохранение исходной сессии без её архива. Для старых файлов прямо указано отсутствие заданий, для v2 — также списка заклинаний. Отсутствующий массив quests у v4 отклоняется до подтверждения; полная проверка структуры остаётся на сервере. Перенос выполняется через сохраняемую очередь с прежним ключом при потере ответа/перезагрузке. Выбор файла сам по себе ничего не записывает. Интерфейс редактирования заданий пока не подключён.


### Интерфейс заданий кампании

«Задания → Задания моей кампании» открывает серверный список с названием, описанием, статусом и числом выполненных этапов. Форма создаёт и редактирует задания, добавляет/убирает этапы и отмечает выполнение. До 50 этапов; ID существующих этапов сохраняются. Статус выбирается вручную, награды не начисляются. Импортированные задания помечены. Ниже кнопки на основной странице остаётся явно обозначенный демо-сюжет; его отметки независимы.

Запись использует сохраняемую очередь quest-create/quest-update; транспорт превращает её в POST /api/quests с operation=create/update. Ключ и ID не меняются при повторе после потери ответа. Контекст и ревизия проверяются при загрузке списка и отправке формы. До нажатия «Сохранить задание» правки существуют только в открытой форме; закрытие/перезагрузка их не сохраняет. Удаление целого задания и автоматические награды не реализованы.


### Собственные места кампании и перенос v5

GET `/api/places` возвращает `{revision, context, places}`. Место: `{id,campaignId,createdSessionId,title,description,x,y,visited}`, а у импортированного места дополнительно importedFrom. POST с защитными заголовками принимает `{mutationId,expectedRevision,campaignId,placeId,operation,place}`. operation=create/update, place строго `{title,description,x,y,visited}`. Название непустое до 200 символов, описание до 12000; x/y — конечные числа 0–100, visited — boolean; до 1000 мест на кампанию. Координаты относительные на условной схеме, не географические и не расстояния. Удаление и загрузка фонового изображения пока не реализованы.

Новые таблицы campaign_places/place_changes/place_origins создаются без изменения прежних данных. Операции используют общую ревизию, атомарную историю и безопасный повтор. Старая ревизия, чужая кампания, занятый ID — 409; неизвестное/чужое место при update — 404; неверные поля — 422. Обычное сохранение, новая сессия и переключение не теряют места. Источником создания остаётся первоначальная сессия.

GET `/api/export/active-v5` отдаёт JSON v5: контракт v4 плюс обязательное `places: [{origin:{campaignId,placeId,sessionId},place:{title,description,x,y,visited}}]`. Импорт через прежний POST /api/import/active переносит всё одной транзакцией в новую игру. ID мест новые; локальная сессия создания — сессия импорта, первоначальные ID сохранены в importedFrom. Повтор исходной пары campaignId/placeId отклоняется. Повторный экспорт сохраняет первоначальное происхождение. V2–v4 при непустом списке мест отказывают с 409; импорт прежних версий и их нормализованные ключи повторов сохранены. Legacy v1 остаётся частичным экспортом. Лимит импорта 512 КиБ неизменен.

Клиент экспортирует v5 и принимает v1–v5 с предпросмотром числа мест и отсутствия их в старых форматах. Экран карты показывает собственную схему, список по 20 мест, поиск по названию/заметке и фильтр посещения. Отметки схемы соответствуют текущей странице списка. Форма позволяет выбрать положение касанием или ползунками. Демо-карта находится в отдельном раскрываемом блоке; автономный HTML остаётся демо. Запись места входит в сохраняемую очередь, устаревший ответ другой кампании не заменяет карту. До отправки правки формы не сохраняются автоматически.


Основной экран «Задания» теперь показывает серверные карточки без дополнительного окна, поиск по названию/описанию/этапам и фильтр статуса, по 12 карточек на странице. Первые три этапа видны сразу, остальные раскрываются. Быстрая отметка использует POST /api/quests update и прежнюю очередь; статус задания не меняется автоматически. После сохранения в той же кампании сохраняется страница списка и фокус этапа. Демо-сюжет свёрнут отдельно. Старый диалог списка оставлен для совместимости внутренних переходов.


### Предложения событий и перенос v6

GET `/api/proposals` возвращает `{revision,context,proposals}` только для активных кампании, сессии и персонажа. POST `/api/proposals` принимает строго `{mutationId,expectedRevision,campaignId,sessionId,characterId,proposalId,source,suggestion}`. source: `{kind:"manual-text",speaker,text,offsetMs}`; speaker до 120 символов, непустой text до 12000, offsetMs — целое 0–86400000. suggestion: `{kind:"journal"|"personal-note",title,text}`; непустые заголовок до 2000 и текст до 4000. UI ограничивает исходный фрагмент 4000 символами, чтобы скопировать его в предложение. До 1000 предложений для персонажа в сессии. Создание не добавляет запись в журнал и не меняет ресурсы.

POST `/api/proposals/decide`: строго `{mutationId,expectedRevision,proposalId,decision,content}`. decision=accept требует content `{title,text}` с исправленной записью; dismiss требует null. Только pending в текущем контексте можно решить. Accept атомарно добавляет одну запись в journal или notes, сохраняет appliedEntry и статус accepted. Dismiss сохраняет статус dismissed без записи. Исходная фраза и исходное предложение неизменны. Новая команда для уже решённого события — 409; точный повтор прежнего ключа возвращает квитанцию без повторного применения. Проверки контекста, ревизии, HTTP Origin и защищённых заголовков общие. Ошибка истории откатывает и решение, и запись. Переполнение журнала не меняет pending. Возврат решения в pending пока не предусмотрен.

Новые таблицы event_proposals/proposal_changes/proposal_origins не меняют прежние данные. После завершения сессии предложения остаются в SQLite и доступны через архивный просмотр; применять их нельзя. Пользователь предупреждён перед переходом. Архив журнала с принятыми сюжетными записями доступен как прежде, личные заметки остаются у персонажа.

GET `/api/export/active-v6`: контракт v5 с schemaVersion=6 и обязательным `proposals: [{origin:{campaignId,sessionId,characterId,proposalId},source,suggestion,status,appliedEntry}]`. pending/dismissed имеют appliedEntry=null; accepted — валидную запись соответствующего типа. Экспорт включает предложения только текущего контекста. POST `/api/import/active` проверяет состав и уникальность происхождения, создаёт новые локальные ID, сохраняет первоначальные origin и статусы одной транзакцией. Принятые записи уже находятся в state файла и повторно не применяются. Данные файла не доказывают внешнюю подлинность. V2–v5 при наличии предложений отказывают с 409; прежние импорты и нормализованные ключи совместимы. Полный архив и история требуют SQLite backup, HTTP-лимит 512 КиБ сохраняется.

«Журнал» содержит ручную форму источника, списки ожидающих/записанных/пропущенных событий по 10 и экран проверки с исходной фразой и редактируемым результатом. Решения используют сохраняемую очередь; устаревшие формы не пишут в другой контекст. Настройки экспортируют v6, принимают v1–v6, показывают количество предложений до подтверждения. Распознавания аудио и автоматического извлечения смысла нет.


### Архив исходных событий

GET `/api/sessions/{id}/review` возвращает единый снимок `{revision,context,characterName,session,proposals}`. Сессия должна принадлежать активной кампании, иначе 404. Журнал общий для сессии; proposals ограничены выбранным персонажем, кампанией и запрошенной сессией. Чтение выполняется в одной транзакции и не меняет активный контекст, ревизию или ресурсы. Отдельного способа применять архивные предложения нет. Это локальная изоляция контекста, не авторизация пользователей.

«Сессии → Журнал и события» позволяет переключить журнал и исходные события, искать исходную фразу/говорящего/первоначальный и исправленный текст, фильтровать решения, просматривать по 10 записей. Исходная фраза раскрывается отдельно. Pending в архиве подписан «Не разобрано до завершения». Личное событие показывает сохранённую квитанцию принятия, а не текущее содержимое заметок персонажа. Чужой или устаревший ответ не подменяет открытый контекст; закрытый диалог не открывается снова после позднего ответа. Архив не входит в JSON v6; полная копия — SQLite backup.


### Дополнительные персонажи

POST `/api/characters` с обычными защитными заголовками принимает строго `{mutationId,expectedRevision,campaignId,characterId,template,profile:{name,tagline}}`. Только template=bard5-demo, имя непустое до 80 символов, описание до 160; ID 8–80 букв/цифр/дефисов, максимум 100 персонажей на кампанию. Это явный стартовый шаблон с 28/38 хитами, 124 зм и ресурсами барда 5 уровня, не копия текущего героя и не конструктор классов. Новые заметки, инвентарь, список заклинаний и предложения пусты.

Создание допускается только в активной кампании и сразу выбирает нового героя в текущей сессии. Запись персонажа, переключение, общая ревизия, история и квитанция атомарны. Старая ревизия/чужая кампания/занятый ID — 409, поля/шаблон/лимит — 422. Повтор исходной команды не создаёт дубль, не переключает повторно после ухода и возвращает affectedContext исходного создания. При сбое истории новый герой не остаётся в базе. Переключение существующих героев использует POST /api/context/select, проверяющий принадлежность одной кампании и запрет архивной сессии.

«Кампании» показывает кнопку выбора каждого персонажа и создание в активной кампании. Форма и список защищены проверкой контекста/ревизии; команда создания сохраняется в очереди с прежним ID при потере ответа. В заголовке всегда имя выбранного героя. Новые записи механических действий в общем журнале содержат его имя в тексте; старым записям автор не приписывается задним числом. Источники событий и личные записи ограничены выбранным героем. Журнал сессии общий; это ещё не модель прав доступа. Перенос v6 включает только выбранного героя и его источники, остальные персонажи требуют полной копии SQLite.


Каталог также поддерживает GET/POST `/api/catalog/bundled`, GET `/api/catalog/entry?id=...`, POST `/api/catalog/import/preview` и POST `/api/catalog/import`. Форматы и ограничения описаны в [catalog.md](catalog.md). Эти операции не меняют игровой прогресс и не используют его общую ревизию. POST защищены теми же локальными заголовками.


## Фильтры и охват каталога — 19.10

`GET /api/catalog`: дополнительные необязательные параметры `level=0..9` только с `kind=spell`; `school` (одна из восьми школ), `ritual=true|false`, `concentration=true|false` также только с `kind=spell`; `challenge=0|1/8|1/4|1/2|1..30` только с `kind=monster`; `rarity=common|uncommon|rare|very-rare|legendary|varies` только с `kind=item`. Сочетаются с `q`, `limit`, `offset`. Записи без соответствующей структуры исключаются выбранным фильтром. Неизвестные, повторные, неканонические и несовместимые параметры дают 400, а не игнорируются.

Ожидаемые размеры: 24/49/54/42/31/37/31/20/16/15; подготовлено столько же на каждом уровне; установленные версии учитываются отдельно. Это охват SRD, не всех книг игры.

`GET /api/catalog/spell-inventory` возвращает только перечень источника: `ruleset`, `scope`, `sourceUrl`, `entries[{id,nameEn,page,level,school,nameRu,status}]`. `nameRu=null`, если карточка не подготовлена. `status`: `missing`, `prepared`, `installed`, `update-available`, `conflict`. Изменённый личный материал под занятым ID имеет `conflict`; запрос ничего не заменяет и не меняет ревизию игры. Применяется общая защита Host/Origin. Это не список заклинаний персонажа.

Личная книга читает существующий `GET /api/spellbook`, проверяет контекст и ревизию и фильтрует сохранённые записи на клиенте по RU/EN, отметке, уровню, ритуалу и концентрации. Неизвестные поля не равны false. Черновик фильтров переживает смену темы/ревизии своего героя, но сбрасывается при смене персонажа. Ручная отметка по-прежнему отправляется командой `spell-set`; поздний ответ старого персонажа отбрасывается. Магические эффекты и ограничения класса не вычисляются.


### Дополнительные фильтры бестиария и предметов

GET `/api/catalog` принимает `monsterType` (14 типов из схемы) и `size` (tiny/small/medium/large/huge/gargantuan) только при `kind=monster`; они сочетаются с `challenge`. `itemType` (armor/potion/ring/rod/scroll/staff/wand/weapon/wondrous) и `attunement=true|false` доступны только при `kind=item`, вместе с `rarity`. ### Разделы механик

`GET /api/catalog?kind=mechanic&mechanicCategory=combat` фильтрует структурированные механики. Допустимы `condition`, `spellcasting`, `combat`, `rest`, `equipment`, `exploration`; пустое, неизвестное, повторное значение или другая категория дают 400. Справочная ссылка без структуры исключается при фильтрации. Раздел отображается в карточке; правила не применяются к прогрессу автоматически.


## Проверенные обновления каталога — 20.10

GET `/api/catalog/bundled` возвращает `added`, `updated`, `unchanged`, `updates:[{id,name,fromVersion,toVersion,reason}]`. `version` учитывает пакет и правила обновлений. POST принимает прежний контракт с этой версией; повторно проверяет фактические данные внутри общей транзакции. Только совпадение старого и нового SHA-256 из `catalog/bundled-upgrades.json` разрешает замену. Любой иной конфликт или сбой откатывает и добавления, и обновления. Повтор установки возвращает нулевые added/updated. Личный импорт не получает права обновления.

`update-available` в перечне заклинаний позволяет открыть установленную прежнюю карточку; это не конфликт личной версии. `installed` в охвате считает только актуальные точные версии, `upgradable` отдельно сообщает доступные переходы.

Экспорт v2–v6 сохраняет снимок карточки персонажа и его зависимости. При известном переходе к текущему каталогу старый снимок допустим; неизвестное отличие даёт 409. Импорт такого экспорта сохраняет текущую карточку глобального каталога и прежний снимок персонажа. Схема переноса остаётся v6, ресурсов и истории каталог не меняет.


## Справочные заряды и инвентарь — 20.10

Каталог принимает необязательное `item.charges: {max, recharge}` с теми же ограничениями, что `artifact.charges`: целое max 1..10000 и непустое описание восстановления до 2000 символов. Неизвестные поля, дроби, строки вместо числа и пустое восстановление отклоняются атомарно. Старые материалы без этого поля не меняются; версия пакета остаётся 1. В /api/inventory и переносе v2–v6 charges входят только в сохранённый entry; отдельного счётчика текущих зарядов нет.

Клиент инвентаря фильтрует ответ GET /api/inventory по названию RU/EN и явному `attunement=true|false`, выводит по десять записей. Неизвестное требование не равно false. Артефакты участвуют в фильтре. Поиск, страницы и чтение не отправляют команды; индексы действий относятся к исходному ответу, а не к позиции в отфильтрованном списке. Применённые фильтры сохраняются при возврате к тому же герою, сбрасываются для другого героя и после перезагрузки страницы. Устаревшая форма не меняет новый контекст.

«Правила и связи в справочнике» читает актуальную карточку через существующий GET /api/catalog/entry, затем связанные материалы. Этот режим не предлагает повторное добавление предметов или заклинаний. Возврат сохраняет исходный снимок; запоздалый ответ после закрытия окна, смены формы или контекста не открывает справку заново. Фактические настройка, заряды и магические эффекты по-прежнему ручные.


## Поиск описаний и проверка версии вкладки — 20.10

`GET /api/catalog` принимает `scope=name|text`, по умолчанию `name`. `text` расширяет буквальный поиск `q` на поле `text` записи, сохраняя поиск RU/EN имён и все фильтры/пагинацию. Источник, атрибуция и условия лицензии в поиск не входят. Пустые, неизвестные и повторные параметры scope дают 400. Поиск не изменяет каталог или ревизию.

Клиент при `visibilitychange` → visible и по кнопке ↻ выполняет существующий `GET /api/workspace`, только в готовом состоянии без несохранённой команды. Одновременные проверки объединяются; поздний ответ после записи или загрузки другого контекста игнорируется. Отличие ревизии в любую сторону либо контекста включает состояние `stale` без подмены экрана и формы. Записи блокируются существующими проверками готовности; явное «Обновить игру» загружает серверное состояние, только когда диалог закрыт. Ошибка фоновой проверки не подменяет данные и не отменяет проверку ревизии сервером при сохранении. Это не фоновая синхронизация данных и не сохранение ещё не отправленного текста формы.


## Текущие заряды и перенос v7 — 20.10

`POST /api/inventory/charges`: `{mutationId,expectedRevision,characterId,catalogId,unit,operation,amount}`. `unit` — индекс экземпляра с нуля, в пределах quantity; операция `set`, `spend`, `recover`, `unknown`. Для unknown amount строго null; set принимает целое 0..max, расход/восстановление — положительное целое. Неизвестный остаток сначала нужно явно задать. Итог всегда 0..max сохранённой карточки предмета/артефакта. Нулевой запас не уничтожает предмет и не применяет эффект. Справочные карточки не изменяются.

`GET /api/inventory` возвращает необязательное `chargeCounts` — массив quantity элементов, каждый null или целое. Если все неизвестны, поле отсутствует, как у прежних клиентов. Добавление к стопке дописывает null, списание количества удаляет последние элементы. Нумерация отражает позицию в текущем списке; это не глобальный ID предмета. Общая ревизия защищает от команд со старой нумерацией. Изменения входят в inventory_changes, общую историю, идемпотентные квитанции и отмену последней операции. Таблица inventory_charges имеет составной внешний ключ к inventory с каскадным удалением.

`GET /api/export/active-v7` расширяет v6 необязательным chargeCounts у inventory. Максимум проверяется по экспортированному снимку; длина массива совпадает с количеством. Импорт атомарен, дубли и некорректные числа отклоняются. Все-null нормализуется к отсутствию поля. V2–v6 при наличии известных зарядов отвечают 409; старые файлы и прежние нормализованные ключи команд совместимы. UI экспортирует v7.

## Закрытый сервер за прокси — 20.10

`SKAZ_PUBLIC_ORIGIN=https://host` разрешает ровно один HTTPS origin без пути, пользователя и пароля. Node продолжает слушать только 127.0.0.1; Host должен соответствовать локальному порту. Заголовки X-Forwarded-* не используются для расширения доверия. HTTPS-прокси устанавливает upstream Host и сам защищает все страницы/API паролем. Сам по себе параметр PUBLIC_ORIGIN не является авторизацией. Локальный режим по умолчанию не меняется.

Ответы содержат `X-Skaz-Mode: local|private-server`, health отражает режим. Клиент показывает, где сохранён прогресс. Вход на текущем закрытом сервере общий; отдельные роли и учётные записи ещё не реализованы. Независимый выбор игры описан ниже. `SKAZ_BACKUP_DIR` задаёт папку резервных копий вне каталога релиза.

## Независимый выбор игры в окнах — 20.10

Клиент передаёт `X-Skaz-View` с ID вкладки из sessionStorage во всех запросах прогресса. Значение — 8–80 букв ASCII, цифр или дефисов; неверный заголовок даёт 400. При первом обращении создаётся запись `browser_contexts`, копирующая прежний контекст по умолчанию. Новый выбор, создание героя/кампании и импорт переключают только это окно. Чтение листа, инвентаря, книги, заданий, карты, предложений и экспорт используют его выбор. Перезапуск сервера и перезагрузка вкладки сохраняют выбранного героя. После закрытия вкладки новая обычно получает новый ID и исходный выбор.

При поддержке Web Locks дублирование вкладки получает отдельный ID: копия sessionStorage не позволяет отправить чужой сохранённый черновик. Без Web Locks клонированная вкладка может сохранить прежний ID; для независимой игры открой адрес в новой вкладке вручную. ID окна не является секретом, пользователем, членством в партии или проверкой прав. Общий вход по-прежнему разрешает выбор любого персонажа. Запросы без заголовка сохраняют прежний общий контекст для совместимости.

Глобальная ревизия пока общая: изменение в любом окне может потребовать явного обновления остальных, но не переключит их на чужого героя. Квитанция команды связана с ID окна; точный повтор из него безопасен, из другого окна — 409. Не изменяй ID или expectedRevision у неотправленной команды. Черновик, созданный старой версией до введения заголовка, при уже подтверждённой записи может потребовать скачать его и явно загрузить актуальное состояние вместо повторной отправки.

Начало следующей сессии — общее действие кампании: все связанные окна переходят из архивируемой сессии в новую, сохраняя персонажей. Другие кампании не затронуты. Изменение, переход всех окон, ревизия и история записываются атомарно. При повторном запуске после временного отката на старый код выбор архивной сессии исправляется на последнюю неархивную сессию той же кампании.

SQLite backup включает browser_contexts; JSON v7 переносит выбранного персонажа, но не состояние браузерных окон. `workspace.state_json` остаётся снимком контекста по умолчанию; история каждого изменения содержит состояние фактически выбранного героя. Лимит — 10 000 сохранённых ID окон; автоматического удаления/истечения ID нет, чтобы не перенаправить старый черновик на другую игру.


## Черновик формы события — 20.10

Форма «Событие из текста» сохраняет введённые поля в localStorage на каждое изменение. Ключ включает ID вкладки и контекст кампании/персонажа/сессии, но не ревизию; при перезагрузке и повторном открытии той же формы текст восстанавливается. Другие герои, сессии и окна его не подхватывают. Черновик не является серверной записью и не изменяет журнал. Поля подставляются через value, без исполнения HTML. Ошибка хранилища видна рядом с формой и не стирает текст.

После отправки поле formDraftKey остаётся только метаданными браузерной очереди и исключается из HTTP-тела. Черновик удаляется после успешного ответа, в том числе после повтора потерянного ответа; до подтверждения он сохраняется. В «Несохранённых черновиках» доступны также тексты закрытых вкладок и прежних сессий: их можно скачать для чтения/копирования, но это не файл импорта игры. Задания и места также сохраняют ввод по правилам отдельного раздела ниже; другие формы пока не сохраняют незавершённый ввод автоматически. Кнопка создания предложения закреплена, поля прокручиваются отдельно.

## Экспериментальная модель доступа

Сервер содержит `access` и `forUser`, описанные в [access-control.md](access-control.md). Это не новые публичные маршруты: обычный запуск и VPS продолжают работать с общим входом. Доверенный `authenticate` в createApp включает ограниченное чтение без возврата к общему режиму при ошибке личности. Запись forUser проверена также через экспериментальный HTTP-адаптер с individualWrites:true; без authenticate такой флаг запрещён. Обычный server/index.mjs не включает индивидуальные режимы. Владельцы существующих кампаний автоматически не назначаются.

GET /api/me работает только с доверенным authenticate: возвращает {user:{id,displayName,enabled:true},individualWrites} для текущей личности, без чужих данных и с Cache-Control: no-store. Доступен и до назначения первого героя, чтобы будущий клиент мог показать пустое состояние и выбрать пространство черновиков. Отключённый пользователь получает 404, отсутствие личности — 401. В нынешнем общем режиме маршрут возвращает 404. Это не форма входа и не способ передать userId с клиента.


Экспериментальный sessions-адаптер и /api/auth/login, /api/auth/logout описаны в [authentication.md](authentication.md). Обычный запуск их не включает; X-Skaz-Identity не является способом авторизации.

В индивидуальном адаптере GET /api/workspace и ответы команд с state дополнены permissions. Поля: mode="individual", role="owner"|"gm"|"player", boolean character/shared/manageCampaign/catalog/newCampaign/select/import/history/export. В общем режиме поля нет. Метаданные относятся к выбранной кампании; не являются токеном или разрешением обходить серверную проверку. Отзыв/изменение роли применяется к следующему запросу независимо от игровой revision.

## Участники выбранной кампании

Только экспериментальный authenticate + individualWrites:true, владелец кампании:

- GET /api/members → {campaignId,actorId,version,members:[{id,displayName,enabled,role,characterIds}],characters:[{id,name}]}. Чужие ресурсы и заметки отсутствуют. GET допускается владельцу при режиме чтения, но UI и POST управления отключены.
- POST /api/members → тот же актуальный снимок + replayed. Общие поля: action,mutationId,expectedVersion,campaignId,userId. action=set-member требует role=owner|gm|player; remove-member не принимает дополнительных полей; grant-character/revoke-character требуют characterId. expectedVersion — SHA-256 из GET, mutationId — новый устойчивый ключ подтверждённого решения. Нужны JSON и X-Skaz-Client:local-v1; sessions-адаптер также требует точный Origin/проверенную личность. 409 — состав изменился, ключ занят другим решением или попытка отозвать собственное управление; 403 — роль/режим не позволяют; 404 — аккаунт/лист/контекст недоступны; 422 — неверные поля. Запрос ограничен 16 КиБ.

В permissions добавлен boolean members: true только владельцу при включённой записи. Эти маршруты не создают аккаунты/пароли, не заменяют авторизацию, не включаются на общем VPS и не изменяют игровую revision. Подробности повтора, аудита и административной проверки — access-control.md.

## Черновики задания и места

Редакторы задания и места сохраняют незавершённый ввод в localStorage на input/change. Добавление/удаление этапа и выбор точки на схеме также сохраняются. Ключ включает проверенную личность (в индивидуальном режиме), ID вкладки, полный контекст кампании/героя/сессии, базовую revision и ID редактируемой сущности либо new. Это не серверные записи; создание или изменение требует нажатия «Сохранить».

Для той же версии восстанавливаются исходный ID создаваемой сущности, текст, статус, ID/текст/отметки этапов или координаты/посещение. Пустые этапы допустимы в черновике, но не в серверном сохранении. Схема, типы, границы, контекст, режим create/update и ID проверяются перед подстановкой. Некорректный черновик не подставляется. Сбой локального хранилища явно показан рядом с формой.

При смене версии, героя, сессии или вкладки старый ввод автоматически не применяется. Он доступен через «Данные и настройки → Несохранённые черновики»: скачивание формата skaz-form-draft для ручного чтения/копирования, не импорт игры и не автоматическая команда. Список принадлежит текущей личности; прежние общие и чужие черновики не подхватываются в индивидуальном режиме. Очистка истории браузера может удалить эти локальные копии.

После отправки formDraftKey остаётся только в браузерной очереди и исключается из HTTP. Форма удаляется из localStorage после принятого корректного ответа; потеря ответа, отказ прав, конфликт или неверная структура ответа сохраняют текст. Повтор использует исходный ключ/ID/тело очереди. Задание и место используют прежние API/форматы, серверная схема не меняется.

Кнопка сохранения закреплена в нижней части редактора, длинные поля и этапы прокручиваются отдельно. Длинная заметка в карточке задания показывает краткое начало и «Полное описание»; чтение полного текста не требует права редактирования. Расчёт наград и механик не добавлен.


Ручная корректировка ресурсов (20.10) использует существующий PUT /api/workspace: hp/maxHp/gold/inspiration/slots, прежнюю ревизию и mutationId. Нового API/схемы нет. Предпросмотр на клиенте не отправляет запрос; подтверждение создаёт одну команду с неизменными остальными полями. В индивидуальном экспериментальном режиме сервер разрешает её только для назначенного листа с правом записи, без изменения общей кампании/сессии. Пределы текущего шаблона остаются в validateState. Причина входит в label истории, не в общий журнал.


## Ручные характеристики и перенос v8 — 20.10

Workspace дополнен `characterStats`: null для неизменённого шаблона или объект `abilities` (str/dex/con/int/wis/cha, целые 1–30), `armorClass` (0–100), `initiative` (−20…40), `speed` (0–1000 футов). Поля state/schemaVersion 1 не изменялись; значения хранятся отдельно от прежнего JSON. Это ручной лист статистик, не движок классов, владений, эффектов и снаряжения.

POST `/api/character-stats` принимает ровно mutationId, expectedRevision, characterId, stats. stats=null возвращает шаблон, иначе нужна полная структура выше. Общая ревизия, привязка к активному герою, повторяемый ключ, транзакционная запись и аудит; индивидуальный доступ требует назначения листа и права записи. Смена ресурсов обычным PUT не меняет характеристики. Ошибка аудита откатывает всё.

GET `/api/export/active-v8` добавляет обязательное characterStats (объект или null), остальные поля как в v7. Перенос создаёт новую кампанию/героя; старые игры сохраняются. Импорт v1–v7 поддерживается, v2–v7 создаёт героя со статистиками шаблона. При наличии ручных характеристик экспорт v1–v7 отклоняется с 409; клиент также запрещает сокращённый v1 и предлагает v8/SQLite. Предпросмотр v8 показывает значения, пропущенные/неверные характеристики отвергаются. Новые данные включены в полную SQLite-копию.


## Ручной класс, счётчики и перенос v9 — 20.10

Workspace содержит characterSheet: null для прежнего шаблона или {ruleset:"5e-2014",ancestry,className,subclass,level,counters}. Строки до 80 символов, className непустой, общий level — целое 1–20; максимум 20 counters={id,name,current,max}. ID 8–80 букв/цифр/дефисов, уникальные; названия непустые и уникальны без регистра/краевых пробелов. Целые остатки 0≤current≤max≤9999.
