# Локальный API 0.2

Серверный каталог: GET `/api/catalog` и `/api/catalog/coverage`, локальный импорт — см. [формат и ограничения](catalog.md). Каталог хранится отдельно от JSON прогресса.

Node.js 24+, SQLite. Один локальный пользователь, один пример персонажа и кампании. Авторизации и доступа по LAN в этой версии нет. Слушает только loopback; Host и Origin проверяются. Статический сервер выдаёт только явно перечисленные файлы клиента, не базу и не исходники сервера.

## Методы

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/health` | Режим и тип хранилища |
| GET | `/api/workspace` | `schemaVersion`, `revision`, `updatedAt`, `state` |
| GET | `/api/context` | Активные кампания, персонаж и сессия с ID, данными и общей ревизией |
| GET | `/api/campaigns` | Список кампаний и ID их персонажей/сессий |
| POST | `/api/campaigns` | Создать и активировать кампанию из явно переданного state |
| POST | `/api/context/select` | Выбрать кампанию, персонажа и сессию с проверкой общей ревизии |
| POST | `/api/sessions` | Начать следующую сессию активной кампании, архивируя прежнюю |
| GET | `/api/campaigns/{id}/sessions` | Все сессии кампании и метаданные |
| GET | `/api/sessions/{id}` | Журнал сессии и метаданные без переключения игры |
| PUT | `/api/workspace` | Проверка и транзакционное сохранение состояния |
| GET | `/api/history` | Последние 50 изменений без полных снимков |
| GET | `/api/export` | JSON прогресса для переноса |

PUT требует `Content-Type: application/json` и `X-Skaz-Client: local-v1`. Этот заголовок защищает от простых запросов постороннего сайта, но не является авторизацией. Тело:

```json
{
  "mutationId": "уникальный-uuid",
  "expectedRevision": 0,
  "label": "Здоровье восстановлено",
  "state": {}
}
```

`state` в примере сокращён: сервер требует полную структуру из `server/state.mjs`. Тема — локальная настройка браузера и в серверный прогресс не входит. Максимум тела 512 КиБ. Неверные поля или ресурсы возвращают 422; старая версия — 409. Повтор идентичного `mutationId` не создаёт новое изменение, а возвращает актуальное состояние; повтор того же ID с другим содержимым — 409.

В транзакции записываются состояние, версия и запись истории с предыдущим и следующим снимком. Отмена — новое сохранение предыдущего состояния с проверкой версии. Запрос со старой версией не может затереть чужое изменение. Автоматического слияния пока нет.

## Хранение

Начало сессии и чтение архива описаны в [контракте сессий](sessions.md). Архив нельзя активировать для редактирования. Кнопка «Сессии» открывает начало сессии и просмотр журнала/архива. Ответ workspace дополнен полем session с name и playedOn; они могут быть null для прежних сессий.

`data/skaz.sqlite`, путь можно переопределить через `SKAZ_DB`. Раскладка базы v2: `campaigns`, `characters`, `sessions`, `active_context` хранят связанные сущности; `workspace` — ревизию и совместимый снимок; `changes` — историю и ключи повторов. Каталог хранится отдельно. API и JSON-экспорт сохраняют schemaVersion=1. Чтение собирает прогресс из сущностей; все изменения выполняются в общей транзакции. Подробности и условия обновления — [хранение сущностей](entities.md). Создание и переключение игр доступны в API и кнопке «Кампании»; пользователи ещё не реализованы. До многопользовательского режима нужны серверные команды игровых действий вместо передачи полного состояния. Проверка структуры и пределов ресурсов не заменяет полный движок правил D&D.

История снимков растёт вместе с журналом; архивирование пока не реализовано. Рекомендуется регулярно делать резервные копии. `node scripts/backup.mjs` использует SQLite backup API, который корректно снимает копию работающей базы, включая подтверждённые записи при WAL.

## Поведение клиента при сбое

Клиент не показывает успешное сохранение до ответа сервера. Если запрос завершился ошибкой, кандидат остаётся локальным черновиком с прежним `mutationId`. До разрешения сбоя новые изменения блокируются. Повтор запроса безопасен даже если первый ответ потерялся после успешной записи.

Черновики разных вкладок имеют разные ключи; после перезагрузки вкладка находит собственный черновик. Черновики закрытых вкладок доступны в «Данные и настройки → Несохранённые черновики». Их можно скачать и затем импортировать. При конфликте можно скачать свой вариант и явно загрузить актуальное состояние. Автоматического фонового объединения и realtime-обновления других вкладок нет.

Самостоятельный `dist/skaz.html`, открытый через `file:`, остаётся демо в браузере. Серверное приложение запускается отдельно по HTTP. Старое сохранение можно перенести вручную через настройки, если оно доступно на том же origin; файл из другого браузера переносится экспортом и импортом.

Каталог поддерживает необязательную структуру `spell` и режим источника `cc-by-4.0` с обязательными `attribution`/`changes`. Отчёт `/api/catalog/coverage` дополнен `openlyLicensed` и `structuredSpells`. Контракт и ограничения: [catalog.md](catalog.md).

Для kind=item поддерживается необязательная структура `item`: тип, редкость, настройка и формула лечения зелья. `/api/catalog/coverage` дополнен `structuredItems`. Импорт не меняет ресурсы персонажа.

Для kind=monster доступна необязательная структура `monster` с основными характеристиками; `/api/catalog/coverage` дополнен `structuredMonsters`. Дробная опасность хранится строкой (например, `1/4`). Контракт: [catalog.md](catalog.md).

Для kind=mechanic поддерживается необязательное `mechanic: { category: "condition", effects: [...] }`. Coverage дополнен `structuredMechanics`. Ссылки `links` проверяются на наличие целей; применение состояний к персонажу не реализовано.

Для kind=artifact поддерживается необязательное `artifact` с типом, настройкой и максимумом/описанием восстановления зарядов. Coverage дополнен `structuredArtifacts`. Текущий запас зарядов экземпляра в каталоге не хранится.


## Инвентарь: серверный этап

GET `/api/inventory` возвращает `revision`, `context` активной игры и `entries`: `{catalogId, quantity, entry}`. `entry` — снимок записи каталога при первом добавлении, включая источник. Список относится только к активному персонажу.

POST `/api/inventory` требует обычные локальные защитные заголовки и тело:

```json
{"mutationId":"unique-mutation-id","expectedRevision":0,"characterId":"active-character-id","catalogId":"srd51:2014:item:potion-of-healing","quantity":2}
```

Количество — целое 1–999, суммарно на вид предмета не более 999, до 1000 видов у персонажа. Допустимы только item/artifact редакции 2014, уже существующие в каталоге. Для справочных ссылок не подразумевается наличие полных характеристик. Несовпадение активного персонажа или ревизии — 409; отсутствующий материал — 404; неверные значения/категория — 422. Неизвестные поля команды — 400.

Ответ POST — обычный workspace и affectedContext; список нужно читать GET. Идентичный повтор возвращает актуальную игру и первоначальный affectedContext, не переключает персонажа и не увеличивает количество снова. Золото не списывается: это добавление имущества, не покупка. Здоровье, бонусы и настройки предметов не меняются.

Таблицы inventory и inventory_changes добавляются без преобразования старого state. Инвентарь связан с персонажем, не с сессией. Общая ревизия/история/квитанция и отдельные снимки инвентаря записываются атомарно. Старые сохранения листа не заменяют инвентарь. SQLite backup включает всё. **JSON экспорта/импорта прогресса v1 пока не включает и не восстанавливает инвентарь**; до отдельного формата переноса используйте SQLite backup. Автоматического преобразования нарисованных демо-предметов нет.

Уменьшение количества доступно через серверную команду ниже; экипировка, индивидуальные заряды и применение эффектов зелий пока не реализованы. Количество пока группируется по ID каталога, отдельные экземпляры артефактов не моделируются.

Клиент: «Герой → Инвентарь → Открыть» читает список, карточка предмета/артефакта в справочнике открывает форму количества с именем персонажа и кампании. Команда добавления использует общую сохраняемую очередь: повтор после сбоя/перезагрузки сохраняет mutationId, characterId и expectedRevision. Конфликт блокирует новые изменения до явного обновления. Чтение инвентаря другой ревизии не принимает её молча. JSON v1 не заменяет инвентарь; ограничение указано в настройках.


### Списание количества (сервер)

POST `/api/inventory/remove` принимает те же поля и защитные заголовки, что добавление: `mutationId`, `expectedRevision`, `characterId`, `catalogId`, `quantity`. Количество — положительное целое 1–999, не больше остатка. При полном списании строка исчезает из текущего списка, а прежний снимок с источником остаётся в истории. Это учёт потери, передачи или расхода имущества: лечение, золото и другие ресурсы не меняются.

Отсутствующая строка инвентаря — 404; недостаточный остаток или неверное количество — 422; чужой активный персонаж, старая ревизия или повтор ключа с другой командой — 409. Ключ добавления нельзя использовать для списания. Одинаковый повтор списания не выполняется снова, даже после полного расходования или смены игры; ответ содержит актуальный workspace и первоначальный affectedContext. Списание, ревизия и история атомарны. Ошибка записи истории откатывает даже полное удаление строки. Серверная отмена описана ниже; списание и отмена доступны в окне инвентаря.


### Отмена последней операции инвентаря (сервер)

POST `/api/inventory/undo` с обычными защитными заголовками принимает `{mutationId, expectedRevision, characterId, targetMutationId}`. Все поля обязательны. targetMutationId — ID добавления или списания. Отменяется только последняя операция всей игры: её ревизия должна совпадать с текущей, персонаж — с активным, а инвентарь — с сохранённым результатом исходной операции. Любое последующее сохранение, переключение игры или начало сессии закрывает возможность отмены. Это намеренное ограничение первой версии.

Сервер восстанавливает предыдущий снимок инвентаря вместе с происхождением предметов, создаёт новую ревизию и запись истории, не меняя остальные ресурсы. Неизвестная операция — 404, неверный ID — 422, лишние поля — 400; устаревшая/чужая операция или попытка отменить отмену — 409. Идентичный повтор с тем же mutationId возвращает актуальную игру и первоначальный affectedContext без повторного восстановления. Новый ключ не позволяет отменить ту же операцию второй раз. При сбое истории восстановление откатывается целиком. Кнопки списания и отмены подключены к сохраняемой очереди клиента: после сбоя и перезагрузки отправляется прежняя команда с тем же ключом.


GET /api/inventory дополнен `undo: {mutationId, label} | null`. Сервер возвращает доступную последнюю операцию добавления/списания для активного персонажа. После любого последующего изменения игры или отмены поле равно null. Клиент показывает кнопку отмены по этому полю, в том числе после перезагрузки. Проверка ревизии и исходной операции всё равно выполняется сервером при POST.


### Экспорт активной игры v2 (серверный этап)

GET `/api/export/active` отдаёт скачиваемый `skaz-active-v2.json` без кэширования. Формат: `app: "skaz-active"`, `schemaVersion: 2`, `ruleset: "5e-2014"`, `scope: "active-game"`, `exportedAt`, `source: {revision, context}`, `state`, `session: {name, playedOn}`, `inventory: [{catalogId, quantity}]`, `catalog: {schemaVersion: 1, entries: [...]}`. Источники предметов включены в записи каталога без изменений. В каталог входят только предметы инвентаря и все достижимые связи links, включая транзитивные; циклы не создают дублей. Пустой инвентарь даёт пустой каталог.

Экспорт читает данные в одной транзакции, не меняет ревизию и историю. Отсутствующая зависимость или несовпадение снимка предмета с каталогом возвращает 409 вместо неполного файла. source.context — сведения об исходной игре, не команда переключения на неё.

Охват: активный персонаж, данные активной кампании и текущей сессии, инвентарь с необходимыми материалами. Архивы сессий, другие персонажи/кампании и история изменений не входят; для полной резервной копии остаётся SQLite backup. Старый GET /api/export и отдельная кнопка экспорта без инвентаря сохраняют v1. **Импорт v2 описан ниже и доступен в настройках с предпросмотром**. Новый файл нельзя восстановить существующим импортом v1.


### Импорт активной игры v2 (серверный этап)

POST `/api/import/active` требует локальные защитные заголовки и `{mutationId, expectedRevision, destination: "new-campaign", file: <экспорт v2>}`. Создаёт и активирует новую кампанию, персонажа и сессию с новыми ID. Существующие игры не заменяются. Исходные ID и дата экспорта проверяются как метаданные, но не управляют назначением. Ресурсы, текущий журнал, метаданные сессии (включая null), инвентарь и источники переносятся; архивы и история из исходной базы отсутствуют в формате.

Проверяются точные поля, редакция 2014, состояние, дата/название сессии, структура каталога, уникальные ID, числовые поля, количества 1–999, до 1000 видов предметов и до 1000 записей каталога. Каждая связь должна находиться внутри файла. Совпадающие записи существующего каталога используются повторно; конфликт содержимого под тем же ID даёт 409 без перезаписи. Новые материалы, игра, инвентарь, общая ревизия и история записываются одной транзакцией. Повтор той же нормализованной команды возвращает актуальную игру и первоначальный affectedContext, не создаёт ещё одну кампанию. Импорт не доступен для отмены инвентаря.

HTTP-лимит тела пока 512 КиБ, как у остальных команд; большие экспорты нужно переносить SQLite backup до расширения механизма. Формат v2 не является полной копией базы. В настройках доступны скачивание v2 и предпросмотр импорта с явным созданием новой кампании.

Клиент перед отправкой проверяет размер сериализованной команды целиком (512 КиБ), включая служебные поля. Импорт сохраняется в очереди с прежним ключом при сбое/перезагрузке. Экспорт v2 читает серверный снимок и отказывается скачивать его при несовпадении контекста или ревизии с открытой игрой.


### Список заклинаний персонажа (серверный этап)

GET `/api/spellbook` возвращает `{revision, context, entries: [{catalogId, status, entry}]}`. POST на тот же путь с локальными защитными заголовками принимает `{mutationId, expectedRevision, characterId, catalogId, status}`. status: `known` (изучено), `prepared` (подготовлено) или `remove` (убрать из списка). Это ручные отметки игрока, а не проверка правил класса: доступность заклинания, лимиты подготовки и допустимый уровень пока не вычисляются. Допустимы только записи spell редакции 2014, включая справочные ссылки; снимок сохраняет источник первого добавления. Максимум 1000 записей у персонажа.

Изменение статуса не расходует ячейки, не меняет концентрацию, хиты или журнал. Список сохраняется при обычном сохранении и начале сессии, изолирован по персонажу. Нет строки при remove — 404, неверная категория/статус — 422, устаревшая ревизия/чужой активный персонаж — 409. История, список и ревизия атомарны; повтор безопасен после перезапуска и переключения игры. Таблицы character_spells и spell_changes добавляются без изменения старых данных.

В интерфейсе магии сохранённый список каталога открывается отдельной кнопкой; ниже остаются восемь демо-заклинаний. JSON v1/v2 не включает этот список; серверный формат v3 и SQLite backup включают его. known/prepared — взаимоисключающие отметки одной записи, переход между ними не создаёт дубль.


### Перенос списка заклинаний: v3

GET `/api/export/active-v3` возвращает `skaz-active-v3.json`: тот же контракт активной игры, но schemaVersion=3 и обязательное `spellbook: [{catalogId, status}]`. Статусы known/prepared; снимки источников и все достижимые связи входят в общий catalog. Каталог включает объединение материалов инвентаря и заклинаний без дублей. Старый экспорт v2 возвращает 409 при непустом серверном списке заклинаний, чтобы не потерять его незаметно.

POST `/api/import/active` принимает v2 и v3. В v3 проверяются наличие списка, не более 1000 записей, уникальность, статус и категория spell. Записи и история заклинаний входят в общую транзакцию импорта. V2 создаёт игру с пустым списком; нормализованный запрос v2 не изменён, чтобы сохранить совместимость уже записанных ключей повторов. HTTP-лимит 512 КиБ остаётся общим.

Настройки экспортируют v3 и принимают v1/v2/v3. Предпросмотр v3 показывает число заклинаний, а для v2 явно сообщает об их отсутствии. В v3 отсутствие списка отклоняется до подтверждения. Карточки заклинаний справочника открывают форму ручной отметки, список персонажа — просмотр и изменение/удаление. Команды проходят через сохраняемую очередь и повторяются с тем же ключом при сбое.


### Задания кампании (серверный этап)

GET `/api/quests` возвращает `{revision, context, quests}` активной кампании. Задание: `{id, campaignId, createdSessionId, title, description, status, steps}`. POST с обычными защитными заголовками принимает `{mutationId, expectedRevision, campaignId, questId, operation, quest}`; operation=create/update, quest содержит ровно `{title, description, status, steps}`. Клиент задаёт постоянный questId (8–80 латинских букв/цифр/дефисов). При создании сервер связывает задание с текущей сессией; последующее редактирование эту связь не меняет.

Название 1–200 символов, описание до 12000, статус active/completed/failed. До 50 этапов `{id,title,done}` с уникальным ID, непустым заголовком до 500 символов и булевым done; до 1000 заданий в кампании. Статус задания не выводится автоматически из этапов, награды и ресурсы не начисляются. Сохраняется порядок этапов. Удаления пока нет.

Старая ревизия, чужая активная кампания или занятый ID при создании дают 409; update отсутствующего/чужого задания — 404; неверные поля — 422. Запись, общая ревизия и quest_changes атомарны. Повтор не создаёт дубль и возвращает исходный affectedContext даже после смены игры. Обычное сохранение и новая сессия задания не заменяют.

Интерфейс пока показывает прежние демо-задания; новая модель не преобразует их автоматически. Перенос JSON v1/v2/v3 пока не содержит новые задания; SQLite backup содержит. До подключения UI следующий этап — перенос заданий с новыми ID и корректной связью с импортируемой сессией.


### Перенос заданий: v4 (серверный этап)

GET `/api/export/active-v4` возвращает `skaz-active-v4.json`: контракт v3 с schemaVersion=4 и обязательным `quests: [{origin, quest}]`. quest содержит title, description, status, steps по правилам POST /api/quests. origin содержит исходные campaignId, questId, sessionId. Экспорт включает все задания активной кампании, в том числе созданные в архивных сессиях. Сами архивные журналы не включаются. Порядок заданий/этапов сохраняется. Пустой список обязателен; максимум 1000 заданий. Повтор исходной пары campaignId/questId, неверные поля, ID, статусы и этапы отклоняются (422).

POST `/api/import/active` принимает v4 с прежним destination=new-campaign. Задания получают новые UUID; createdSessionId указывает на локальную сессию импорта. Это время появления записи в новой базе, а не утверждение о том, в какой сессии произошло событие. Исходные ID сохраняются отдельно в quest_origins; GET /api/quests для импортированного задания дополнительно возвращает `importedFrom: {campaignId, questId, sessionId}`. Эти сведения заявлены файлом, не являются внешними ключами и не дают доступа к исходной игре. Исходная сессия может отсутствовать в новой базе. Повторный экспорт сохраняет первоначальное происхождение, редактирование его не меняет. ID этапов сохраняются внутри нового задания.

Создание кампании, заданий, происхождения, инвентаря, заклинаний, каталога и общей записи импорта атомарно. Общая история фиксирует операцию import-active; отдельные quest_changes возникают при последующих редактированиях. Повтор ключа импорта после перезапуска не создаёт дубли. Старые нормализованные команды v2/v3 сохранены. Экспорт v2/v3 при непустом списке заданий возвращает 409 с подсказкой использовать v4 или SQLite backup. Legacy v1 остаётся ограниченным экспортом прогресса без этих сущностей.

HTTP-лимит 512 КиБ сохраняется. Клиент настроек пока экспортирует v3, принимает v1/v2/v3; v4 пока доступен только через API. Изменений интерфейса в этом этапе нет.


### Перенос v4 в настройках

Клиент экспортирует v4 и принимает v1/v2/v3/v4. Предпросмотр показывает число заданий и объясняет сохранение исходной сессии без её архива. Для старых файлов прямо указано отсутствие заданий, для v2 — также списка заклинаний. Отсутствующий массив quests у v4 отклоняется до подтверждения; полная проверка структуры остаётся на сервере. Перенос выполняется через сохраняемую очередь с прежним ключом при потере ответа/перезагрузке. Выбор файла сам по себе ничего не записывает. Интерфейс редактирования заданий пока не подключён.
