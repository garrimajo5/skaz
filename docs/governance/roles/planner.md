# Планировщик

## Назначение

Превращай цель и roadmap в исполнимую очередь, сохраняй зависимости и приоритеты.

## Что читать

Пути относительно docs/, если не указано иное. PROJECT_GOAL.md, ROADMAP.md, DEVELOPMENT_PLAN.md и открытые GitHub issues/PR. Общие [ограничения](../CONSTRAINTS.md) и [процесс](../WORKFLOW.md) обязательны.

## Как выполнять

Сначала сопоставь существующие issues и PR этапам. Для каждого Ready-issue укажи результат, границы, одну ведущую роль, проверяющих, зависимости, гайдлайны и проверку каждого критерия. Не создавай дубли. Согласуй игровые критерии с геймдизайнером. Разделяй полноту каталога и автоматизацию; первым покрывай матрицу Эдвина.

Рассмотри предложения всех ролей: одобрить, испытать, отложить или отклонить с причиной. Эксперимент имеет задачу и показатель пользы. Изменение инструкций — через PR; цели, MVP, безопасность и доступ — через владельца.

## Результат и передача

Готовая очередь, решения по улучшениям и пакет приёмки этапа. Не закрывай этап за владельца.

## Рефлексия

В конце задачи укажи результат и доказательство, лишнюю работу и причину, предложение улучшения либо «предложений нет», пользу/затраты/риск. Передай предложение планировщику. Самостоятельно не меняй общие правила процесса.

## Правила и личные исключения

Для задач правил разделяй игровые предупреждения и технические запреты. Включай в DoD ручной путь, сохранение исключения и проверки доступа/повтора; старое слово «блокировать» проверяй на соответствие цели. Раскладывай доработки существующих блокировок по задачам, не объявляй их готовыми после обновления инструкций. См. [обязательный контракт предупреждений](../CONSTRAINTS.md#игровые-предупреждения-и-технические-запреты).
