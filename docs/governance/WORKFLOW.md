# Процесс сессии

## Источники истины

[Цель](../PROJECT_GOAL.md), [roadmap](../ROADMAP.md), [ограничения](CONSTRAINTS.md), [роли](ROLES.md). GitHub issues — задачи и назначения, PR — изменения и доказательства. deployment.md — фактический выпуск. DEVELOPMENT_PLAN — техническая очередь и история, не копия статусов всех issues.

## Выбор и выполнение

1. Прочитать свою роль, цель и изменения применимых правил. Проверить Git, issue, PR и отсутствие другого исполнителя.
2. Выбирать первую доступную задачу по правилу выбора ниже и принимать роль, требуемую её текущим шагом. Для выполнения нужны результат, границы, зависимости и проверяемые критерии. Недостающую постановку готовит планировщик; независимая работа может продолжаться.
3. Для длинного блока выбрать несколько связанных доступных результатов и резервную задачу; одновременно вести одну задачу на сессию. Не заполнять время повторными зелёными тестами или отчётами.
4. Зафиксировать в issue роль, исполнителя, ветку/worktree и время начала. Перед изменениями перепроверить назначение: комментарий не является атомарной блокировкой. При гонке сначала согласовать владельца задачи.
5. Не создавать дубли issues и уже выполненного кода. Сопоставлять старые результаты с новыми критериями по доказательствам.
6. Реализовать в изолированной копии, проверить логику и изменённый интерфейс на вымышленных данных. Полный обязательный набор — перед выпуском; повторять проверки при изменениях или новых рисках. Большие логи хранить в файлах без секретов, в отчёт давать итог.

## Передача и статусы

Предлагаемые статусы (GitHub Project или явное поле issue): Backlog → Ready → In progress → Review → Verified → Released → Awaiting owner acceptance → Accepted.

Исполнитель передаёт в Review с проверкой каждого DoD, ссылками на применимые гайдлайны, ограничениями и доказательствами; UI — с до/после. QA независимо подтверждает критерии, геймдизайнер — игровой результат. Для чисто технической задачи игровая проверка может быть заранее исключена планировщиком с причиной. Если независимой проверки нет, результат остаётся ожидающим её.

Релиз-инженер отмечает Released после выпуска и smoke; для документов указывается принятый артефакт и версия, выпуск приложения неприменим. Обычный issue закрывается по всем своим критериям. Функция, требующая выпуска, не закрывается одним merge; до выпуска использовать Refs вместо автоматического Closes.

Этап roadmap и milestone закрывает только владелец с явным решением. Техническая или игровая приёмка его не заменяет. Провал проверки возвращает задачу исполнителю с дефектом; внешняя блокировка содержит конкретное условие и не мешает независимой Ready-задаче.

## Рефлексия всех ролей

После задачи: результат и доказательство; что вызвало лишнюю работу; предложение улучшения либо «предложений нет»; ожидаемая польза, затраты и риск. Коротко, без секретов и пересказа всей работы.

Планировщик фиксирует решение: одобрить / испытать на одной задаче / отложить / отклонить, с причиной. Эксперимент получает ответственного, задачу и критерий оценки. Одобренные инструкции меняются через PR. Изменения цели, MVP, доступа и безопасности передаются владельцу, а не утверждаются планировщиком единолично.

## Передача следующей сессии

В issue: commit/PR, завершённые критерии, конкретный следующий шаг, проверки, блокировки и свои работающие стенды. Не копировать историю чата и все инструкции, не превращать срочное разрешение в бессрочное. Использовать [шаблон issue](../../.github/ISSUE_TEMPLATE/role-task.md).

## Выбор задачи и роли — уточнение владельца17.11.2026

Брать первую доступную задачу без блокировки владельца: его явный приоритет, затем этапы M0→M5 и зависимости, затем приоритет/номер issue. Роль определяется текущим шагом: постановка, реализация или Review. При переходе явно объявить роль и прочитать её инструкцию; ведущая role-метка не запрещает передачу проверяющему. Отсутствие задач прежней роли не является основанием остановиться: проверить доступные шаги других ролей. Не обходить зависимости, чужое назначение и запреты владельца. Собственная проверка не становится независимой при смене роли; при необходимости независимости передать результат и взять другую задачу. Этапы закрывает только владелец.
